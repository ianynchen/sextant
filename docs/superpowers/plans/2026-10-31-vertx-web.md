# Vert.x Web and WebClient — Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Every route a Vert.x `Router` serves becomes one inbound row per wire identity, with the handler that answers, and every `WebClient` request becomes one outbound row, with its address (the client's configured base included) and body.

**Architecture:**
- **No Vert.x engine.** Two catalogs on the existing `fluent` style: `vertx-web.yml` (inbound) and `vertx-webclient.yml` (outbound), plus `client-models/vertx-web.yml`.
- **General changes, each for every catalog, none naming a Vert.x type:**
  - row markers (pattern path, any-method) and the linker rules that read them;
  - inbound media and the `leading_slash` join, shared with `combinator`;
  - accumulating captures;
  - the inbound dedup key;
  - refused paths recorded, not repaired;
  - a producer-walk end that names the parameter it reached;
  - `passes_on`;
  - `mount` with `router_type`;
  - `host`/`port` captures;
  - an options-object `client_base` rung.
- Quarkus Reactive Routes, the same dispatcher, is brought onto the same rules.

**Tech Stack:** Python 3.13, DuckDB, pytest; Java fixtures built with Maven, JDK 21.

**Spec:** `docs/superpowers/specs/2026-10-30-vertx-web-design.md` (reviewed 2026-10-31; rulings in its §8, taken under the user's delegation for Vert.x).
