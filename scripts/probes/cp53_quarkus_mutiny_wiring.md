# CP-53 — Quarkus's Mutiny client and delegating-bean wiring, measured

**Version scope.** Everything below is measured against `quarkus-grpc-api` and
`quarkus-grpc-deployment` **as their own manifests state them** (`Implementation-Version` —
`3.17.5`, the fixture's Quarkus, when this record was made), read by `probe.py` out of the
local Maven repository — never the directory name this harness found them under, which is the
CP-5 failure the convention exists to prevent. These are build-time behaviour of Quarkus
`3.17.5` and a later release is free to change any of them, so the verdicts here bound to the
version in the table and to nothing wider.

**Why it was measured.** The Quarkus Mutiny gRPC design (spec 2026-10-25, §2b, §3b) gives
Quarkus's two catalogs a client rule and a server rule: an injected service interface is
answered by the generated Mutiny client class that implements it, and a generated Mutiny bean
is served by the user's `@GrpcService` class that implements the interface the bean delegates
to. Both rules are what Quarkus's own build step does, so they are read off its bytecode
(`GrpcClientProcessor.discoverInjectedClients` and `GrpcServerProcessor.processGeneratedBeans`)
before either catalog states them. CP-52 (row 7) already records that every Quarkus service
bean must carry `@GrpcService`; this probe records what the extension does with the generated
classes around it.

## What the rows say

Letters (a)–(d) are the four questions the probe was written to answer.

**(a) Rows 2–3 — a service interface maps to the Mutiny client class that implements it, by
the FIRST interface that is not `MutinyClient`.** `discoverInjectedClients` takes every
direct implementor of `io.quarkus.grpc.MutinyClient`, reads its `interfaceNames`, and keeps
the first interface that is not `MutinyClient` — then stops reading that class's interfaces.
`Map.put` stores that interface as the key and the implementing class as the value. An
implementor with no other interface fails the build. Supports spec §2b's client bullet
("takes every direct implementor of `io.quarkus.grpc.MutinyClient` and keys it by the other
interfaces that class declares") with one correction: it is the first other interface, not all
of them. For the generated client (which declares the service interface and `MutinyClient`)
the two readings agree; they differ only for a class declaring a second unrelated interface,
which the catalog rule should not claim to key.

**(b) Rows 4–7 — an injected type is classified by its type closure, in a fixed order.** The
type is first compared with `io.grpc.Channel`; otherwise `getRawTypeClosure` builds the set of
the class's own name, its interfaces' closures and its superclass's closure (to any depth,
stopping at `Object`; a class the index lacks is added by name alone). Then, in order:
`AbstractBlockingStub` in the set gives a blocking stub, `MutinyStub` a Mutiny stub, and
`MutinyService` a `MUTINY_CLIENT` whose class is the one row 3 mapped (`Map.get` by the
injected type's name); a miss, or a type that passes none of the tests, is a build error. Supports
spec §2b's second client sentence ("`AbstractBlockingStub` gives a blocking stub, `MutinyStub`
a Mutiny stub, and `MutinyService` the mapped client class"), and adds that an injected
interface that is NOT a key of the map fails the build — so the "unresolved row plus question"
of §3b is Sextant's reading of a module Quarkus itself would refuse to build.

**(c) Rows 8–11 — a generated Mutiny bean is served as delegating to one `@GrpcService`
class, and four further conditions apply.** For each direct implementor of `MutinyBean`, the
extension reads its field named `delegate` (absent: the build fails), takes the field's type,
and looks at that type's implementors (`getAllKnownImplementors`). The first implementor
carrying `@GrpcService` on the class itself (`declaredAnnotation`, so not inherited) is the
match; no match skips the bean. Supports spec §2b's server bullet, which says the same in
three sentences. What §2b does not say, and the catalog rule must carry or state as a
deliberate omission:

* the bean's superclass must have exactly one known subclass (the bean itself);
* the superclass's name with `Mutiny` removed must have no known subclass;
* the superclass's name must not start with `grpc.health.v1` or `io.grpc.reflection`;
* where several implementors carry `@GrpcService`, the one taken is the first the index
  yields, which the bytecode does not order. Spec §3b serves *every* such class; the two agree
  when exactly one exists, and with more than one the catalog rule is wider than what Quarkus
  builds (Quarkus delegates to one of them, unspecified which).

The first two are conditions on the *generated* bean's superclass, read here from the
bytecode that tests them; this probe does not open a generated class, so what a superclass
named in them looks like is an inference from the code, not a measurement.

A bean that passes becomes a `DelegatingGrpcBeanBuildItem(bean, match)`; the match's methods
(not the bean's) are read for blocking markers and recorded under the bean's name, and each
recorded bean name becomes a `BindableServiceBuildItem` — the bean is what is served, the
match is where the behaviour lives.

**(d) Row 1 — the four marker types are plain interfaces in `quarkus-grpc-api`.**
`MutinyService`, `MutinyBean` and `MutinyStub` carry no members; `MutinyClient<T extends
AbstractStub<T>>` has `getStub()` and `newInstanceWithStub(T)`. A module that declares
`quarkus-grpc` gets them through that artifact's dependency on `quarkus-grpc-api` (CP-52
row 3), so they are the types a catalog's `implements:` names. Supports spec §2b's use of the
four names and §3b's `implements: io.quarkus.grpc.MutinyClient` / `MutinyBean`.

## What this does NOT measure

* **What the generated classes look like.** The probe reads the build step, not the output of
  `protoc-gen-quarkus-grpc`: that the generated client declares the service interface and
  `MutinyClient`, and that the generated bean has a `delegate` field typed as the service
  interface, is what the conditions above require, not something this probe opened. The
  fixture (spec §3f) is where a generated pair is read.
* **Run-time behaviour.** `generateClientProducers` and what a stub does when called are not
  read; this is only which class the build step picks.
* **Versions other than `3.17.5`.** The field corpus's Quarkus is `3.40.1.1`; its gRPC jars
  were not fetched, so the rows bound to `3.17.5`.
