# CP-54 — Ktor's HTTP client, WebSocket and SSE call shapes, measured

**Version scope.** Everything below is measured against Ktor **3.6.0**: `ktor-http-jvm`,
`ktor-client-core-jvm`, `ktor-server-websockets-jvm` and `ktor-server-sse-jvm` **as their own
manifests state it** (`Implementation-Version` 3.6.0), plus `ktor-client-mock-jvm` 3.6.0 as the
engine the join rows ran on, and `ktor-server-test-host-jvm` and `ktor-server-cio-jvm` 3.6.0 as
the servers the dispatch rows (h) ran on. The probe module is compiled by Kotlin 2.4.20 (the class files carry
Kotlin metadata 2.4.0, the only version kotlinc writes into a class file) for Java 21 bytecode (class file major version 65; the pom sets the Kotlin compiler's `jvmTarget`).
`probe.py` reads each jar out of the local Maven repository and takes the version from the jar,
never from the directory name the harness found it under (the CP-5 failure the convention exists
to prevent), and the process that ran Ktor's own code has to report the same version or the run
aborts. These are shapes of Ktor 3.6.0 and its compiler output; Ktor 1.x and 2.x, a later Ktor
and a different Kotlin compiler are free to change any of them, so the verdicts bound to the
version in the table and to nothing wider.

**Why it was measured.** The Ktor design (spec 2026-10-26, §2, §3) gives Ktor's catalogs five
new jobs: read an HTTP verb from a static field of `HttpMethod`; add WebSocket and SSE server
routes beside the HTTP routes; read the HTTP client's calls although Kotlin inlines them; join a
relative client address onto the base set by `defaultRequest`; and read the WebSocket and SSE
client calls. Every one rests on a fact about Ktor's own bytecode or behaviour that nobody had
written down, and the spec's first draft guessed at several (which argument of `webSocket` is the
path, what the SSE function is called, how a relative address is joined). This record is what
each new or changed Ktor catalog cites in its `measured:` block, so the guesses are replaced by
readings before any catalog states them.

**What this probe does not settle.** It measures what the libraries and the Kotlin compiler
produce for a probe module of our own; it reads no downloaded project and runs no application
(the module is compiled and its `main` runs Ktor's `DefaultRequest` over a mock engine that
opens no connection, and, for rows (h), installs small routing trees of its own in Ktor's test
host and in a CIO server bound to `127.0.0.1` on a free port, sends them requests, and stops
them). Rows (h) measure one server engine, CIO; whether Netty or Jetty complete a WebSocket
upgrade on a verb other than GET is not measured. The verbs `get`, `post`, `put`, `patch`, `delete`, `head`, `options` with
an address string are measured; `trace`, `query`, `submitForm`, `request(HttpRequestBuilder)` and
a request built by hand are not. The SSE client's join of a relative address is not measured: the
mock engine does not offer the SSE capability, so the SSE call stops before it sends anything
(the WebSocket calls were measured). How the real corpora use these calls is the builder's
fixture and corpus work, not this record.

**How to run.** `JAVA_HOME=<jdk 21> bash scripts/probes/cp54_ktor_client_ws_sse/run.sh`. It
compiles `scripts/probes/cp54_ktor_client_ws_sse/module/` with Maven after a `clean` (so no cell
can come from a stale build), asks Maven for the module's classpath, then runs `probe.py`, which
prints the table below. Needs a JDK (for `javap` and `java`), Maven, and network on the first run
only (Ktor 3.6.0 and Kotlin 2.4.20 are cached in `~/.m2` afterwards). Not a test: nothing in the
suite runs it.

## What the rows say

Letters (a)–(j) are the questions the probe was written to answer. Each verdict names the spec
section (`docs/superpowers/specs/2026-10-26-ktor-client-websockets-sse-design.md`) it supports.

**(a) Rows 1–2 — the verbs are static fields, nine of them, and the old getters stop at
`Trace`.** `HttpMethod` declares `Get`, `Post`, `Put`, `Patch`, `Delete`, `Head`, `Options`,
`Trace` and `Query` as public static fields, each built from the matching upper-case word. The
`Companion` still has getters for the first eight, so older code that calls `getGet()` keeps
working, but it has no `getQuery`. A vocabulary of getters alone reads no verb from code that
reads the field, which is what 3.6.0 code does, and could never read `Query`. The
`DefaultMethods` list holds only the first seven. Supports §2d and §3a: the field form is needed
as data beside the getter form, with all nine names.

**(b) Rows 3–15 — the client call is inlined and ends in `HttpStatement`, but the forms are not
one sequence.** For `get("…")`, `get { url("…") }`, `request("…") { method = … }` and
`prepareGet("…")` the order is: `new HttpRequestBuilder()`, `HttpRequestKt.url(builder, string)`,
`builder.setMethod(HttpMethod.<Verb>)`, `new HttpStatement(builder, client)`, `execute()`. The
body-capable verbs (`post`, `put`, `patch`) and also `delete`, `head` and `options` with an
address string set the verb **twice**: once straight after the builder is created, before `url`,
and again at the end, with the same value both times. A body adds `setBody` and `setBodyType`,
each twice; the bytecode has an `instanceof OutgoingContent` test between them, so the two copies are
probably its two branches (an inference from the bytecode, not a measured cause). The
address is a string constant in the same function as the call. The builder is argument 0 of the
`HttpStatement` constructor and the client is argument 1. The relative call (row 14) and the call
on a client made by `config` (row 15) compile exactly like the others; the shape does not show
which client's base applies. Supports §2a and §3c, with one correction to §2a ("all five forms
compile to the same sequence"): the verb is the value of the **last** `setMethod`, which is the
same as the first wherever it is set twice.

**(c) Rows 16–27 — the server routes, and which argument is the path.** `webSocket` has two
current overloads and two hidden old binary forms with the same JVM name (they return nothing;
code compiled by an older Ktor links to them). In the 3-argument overload argument 1 is the
**protocol**, not a path; in the 4-argument overload it is the path and argument 2 is the
protocol. So `path_arg: 1` holds for the 4-argument form only. A call with a path always lands on
the 4-argument form: `webSocket("/ws/chat") { }` as `webSocket$default` with mask 2 (the protocol
left to its default), and `webSocket("/ws/protocol", protocol = "chat") { }` as a direct
`webSocket` (rows 19–20). `webSocket { }` is the 3-argument `webSocket$default` with mask 1, and
`webSocket(protocol = "pathless") { }` a direct 3-argument call; neither has a path (rows 21–22).
`webSocketRaw` has four current overloads: its path is argument 1 only where argument 2 is also a
String (the two forms with a path), and the forms `(Route, String, Function2)` and
`(Route, String, boolean, Function2)` carry a protocol in argument 1 and no path (rows 17, 23–24).
`sse` has four overloads and no `$default` bridge, so a call is always the plain `sse`; the two
3-argument ones are told apart only by argument 1's type (`String` is a path, `Function2` is a
serializer), the 4-argument one has both, and the 2-argument one has neither (rows 18, 25–26). A
call nested in `route("/api") { … }` is an ordinary call carrying only its own relative path;
the `/api` is the enclosing `route` call's string (row 27). Supports §3b and its "Corrections
from the check": the protocol claim is confirmed, `webSocketRaw` is the same, and an overload is
chosen by its descriptor and not by its arity alone.

**(d) Rows 28–45 — the client WebSocket and SSE calls.** The WebSocket functions keep plain names
(`webSocket`, `ws`, `wss`, `webSocketSession`), each with three overloads: request-lambda only,
`urlString` first (argument 1 is the address), and `method, host, port, path` (path is argument
4, port is a boxed `Integer`). The SSE functions all carry a hash-like suffix (the spec reads it as
the compiler's encoding of a `Duration` parameter; this probe records the suffixes, not the
cause): `sse`, `sseSession`, `serverSentEvents` and `serverSentEventsSession`, six
overloads each, with the suffixes in rows 32–35. The suffix does not identify a form by itself:
`sse-Mswn-_c` is both the address form (argument 1 a `String`) and the request-lambda form with
a deserializer (argument 1 a `Function1`), so the descriptor decides where the address is.
`client.sse("https://…") { }` is `sse-Mswn-_c$default` with mask 30 (row 42); with a deserializer
it is `sse-Q9yt8Vw` (row 32). The host form (`sse-tL6_L-A`, with a deserializer `sse-BAHpl2s`)
puts the scheme at argument 1 and the path at 4. A call with host, port and path
(`webSocket$default` mask 17, row 37; `sse-tL6_L-A$default` mask 241, row 43) leaves the method,
scheme and request lambda to their defaults, which is the "assemble scheme, host, port and path"
case. Supports §3d and §3g items 2 and 4. The mangled suffixes are per Ktor version and are
listed as data, not guessed.

**(e) Rows 46–49 — the base address is set through `defaultRequest`, whose `url` is a member.**
`DefaultRequestBuilder` has three URL setters: `url(String)` (an ordinary instance method, not
the extension on a request builder in row 47), `url { … }` taking a lambda over a `URLBuilder`,
and `url(scheme, host, port, path, block)`. So `url { … }` is a separate setter, and a catalog
that wants only the string form reads `DefaultRequestBuilder.url` with the address at its
argument 0. `defaultRequest { url("…") }` compiles to `DefaultRequestKt.defaultRequest
(HttpClientConfig, Function1)`, and the lambda calls the member `url(String)` (row 49); the
other overload adds a `replace` flag whose default the `$default` bridge fills. A client built as
`HttpClient(engine) { … }` is `HttpClientKt.HttpClient(engineFactory, Function1)`, a derived
client is `HttpClient.config(Function1)`, and in both the configuration lambda calls
`defaultRequest`. Supports §3c and §3g item 3: the ladder is the three calls named above, and
`url { … }` is a separate step if the builder wants it.

**(f) Row 50 — a fresh request builder is a GET to `http://localhost`.** The constructor reads
`HttpMethod.Get` into the `method` field, and a run on a fresh builder gives verb `GET` and URL
`http://localhost`. Supports §3c ("with no verb set, Ktor's default is GET"). The URL default
matters in row 57.

**(g) Rows 51–63 — a relative address joins the base the way a browser would resolve it.** The
six required cases (rows 51–56) were run through Ktor's own `DefaultRequest`:
base `…/v1/` plus `orders` gives `…/v1/orders`; base `…/v1/` plus `/orders` gives `…/orders`;
base `…/v1` plus `orders` gives `…/orders` (the last segment of the base is replaced); base
`…/v1` plus `/orders` gives `…/orders`; an absolute address replaces everything; a query on the
call is kept. Four further cases (rows 57–60): with no `defaultRequest` at all a relative address
joins `http://localhost` (row 57); a bare host as the base works as the root (row 58); a query on
the base is appended **after** the call's own query (`?limit=5&key=1`, row 59); a deeper base
directory ending in `/` takes the whole relative path (row 60). A relative WebSocket address
goes through the same join, but Ktor then rewrites the scheme: `ws("/chat")` over an `https` base
reached the engine as `ws://api.example.com:443/chat` (the port 443 is probably the `https` base's default, kept after the
scheme changed; that is an inference, the probe records only the result) and `wss` over an `http` base as `wss://api.example.com/chat`; an absolute `ws://` address
is untouched (rows 61–63). Supports §3g item 1 (confirmed: the spec's example of
`https://api.openai.com/v1/` plus `/chat` is row 52's pattern) and item 2. A WebSocket row that
keeps the whole URL in `path` should decide whether it reports Ktor's rewritten scheme and port
or only the joined path; the record only states what Ktor does.

**(h) Rows 64–78 — which verb each WebSocket and SSE route answers, asked of Ktor's router.**
Rows 16–27 measure signatures and call shapes; these measure what Ktor itself DISPATCHES. Each
tree is installed in a Ktor application and sent real requests, and two things are recorded by
Ktor per request: the verb the server received (an `onCall` hook) and the route node the router
selected (the `RoutingCallStarted` event, fired after resolution and before the handler; "no
route selected" means none matched). WebSocket requests are a raw RFC 6455 handshake over a socket
to a real CIO server, because Ktor's clients refuse to set `Upgrade` by hand and the test host's
WebSocket client sends its handshake as GET whatever verb it is handed (row 78: asked for POST,
the server received GET). SSE requests go through Ktor's own test host. Dispatch was chosen over a
route-tree dump; the selected node's own `toString` shows its selectors anyway.
- A WebSocket route WITH a path answers GET only. `webSocket("/ws")` and `webSocketRaw("/raw")`
  select `/ws/(method:GET)/(header:Connection = Upgrade)/(header:Upgrade = websocket)` for a GET
  and upgrade (101); a POST selects nothing (405) (rows 66–69). Under
  `method(HttpMethod.Post) { webSocket("/ws") { } }` neither verb selects a route: POST is 405,
  GET is 404 (rows 64–65) — a GET node under a POST selector, never dispatched.
- A path-less WebSocket route has NO verb selector: `route("/p") { webSocket { } }` selects
  `/p/(header:Connection = Upgrade)/(header:Upgrade = websocket)` for GET and for POST (rows
  70–71), and under `method(HttpMethod.Post)` the router selects it for POST (row 72) and not for
  GET (row 73). Routing answers any verb; the CIO ENGINE then completes the upgrade for GET only —
  the POST calls fail with "Unable to perform upgrade as it is not requested by the client" from
  `CIOApplicationResponse` (500, rows 71–72). Other engines are not measured.
- `sse("/e")` answers GET only: it selects `/e/(method:GET)`, and POST is 405 (rows 74–75). The
  path-less `route("/q") { sse { } }` selects `/q` itself for GET and for POST, 200 both (rows
  76–77): no verb selector, as `handle { }`.

Supports §3b and §3g item 5 with one correction: SSE rows carry GET only where a path is given;
the path-less `sse { }` serves the scope's verb, or every verb. The WebSocket rows are verbless,
GET-bound where a path is given.

**(i) Rows 79–80 — a client derived by `config { … }` sends to its own base, and inherits
the parent's when it declares none.** The parent is built with `defaultRequest { url(…/p/) }`
and the derived client with `parent.config { … }`, both over the mock engine, and the request is
the derived client's `get("orders")`. Where the derived block declares its own `defaultRequest {
url(…/c/) }`, Ktor sent `https://child.example.com/c/orders` (row 79): the derived client's own
base wins. Where it declares none, Ktor sent `https://parent.example.com/p/orders` (row 80):
`config` keeps the parent's configuration, `defaultRequest` included. Supports §3g item 3: the
`config` call is a rung of the ladder, read after the parent's construction, and its own
`url(…)` — when it has one — is the base. The rows measure a `defaultRequest` installed with its
default `replace = false`; `defaultRequest(replace = true) { … }` is not measured.

**(j) Rows 81–86 — the joins (g) does not cover, and a block that sets its base twice.**
- **A scheme with no host keeps its scheme over the base's host** (rows 81–82).
  `get("gemini-pro:generateContent")` over `https://generativelanguage.googleapis.com/v1beta/models/`
  was sent as `gemini-pro://generativelanguage.googleapis.com:443/v1beta/models/generateContent`
  (and, under the base without its trailing `/`, `…:443/v1beta/generateContent`). `mergeUrls`
  returns early only for a request with a HOST; one with a scheme and no host is merged like a
  relative path, takes the request's scheme, and is written with the base's port because the
  new scheme's default port is not 443. What a reader joins here is not the base's URL.
- **Two or more leading slashes start an authority** (rows 83–84): `//other.example.com/x/y`
  was sent as `https://other.example.com/x/y`, the base's scheme and nothing else of it, and
  `///x/y` as `https://x/y` — host `x`, not a path `/x/y` under the base's host.
- **A block calling `url(…)` twice applies both, in order** (rows 85–86): two absolute
  addresses leave the second (`https://second.example.com/b/orders`); an absolute then a
  relative one resolves the relative against the first (`url("b/")` after `…/a/` gives
  `https://first.example.com/a/b/orders`).

Supports §3g items 1 and 3: the join's early return is on a host, and the setter's value is
the LAST absolute address in the block, a later relative one moving it.

**Where this record differs from the spec's first draft** (flagged for the builder and the
reviewer; the measurement is what it is):
- §2a says all five client forms compile to one sequence. Only the GET-shaped forms do; the
  verbs that take a body, and `delete`, `head` and `options`, set the verb twice (rows 4–10).
- §3b's `path_arg: 1` is right for one `webSocket` overload and for two `webSocketRaw`
  overloads; it is wrong for the others (rows 16–17). The spec's own correction (the protocol is
  argument 1 of the 3-argument form) is confirmed.
- §3d names `sse-Mswn-_c$default` as the SSE function. That name is shared by two overloads and
  is the right one only for the plain `sse(urlString)` call; other forms have other suffixes.
- §3g item 3 allows that `url { … }` might be a separate setter; it is (row 46).
- §3g item 5 says Ktor registers WebSocket and SSE routes under GET. Only the forms with a path
  do (rows 64–69, 74–75); the path-less `webSocket { }` and `sse { }` select no verb at all
  (rows 70–73, 76–77).
- Not in the spec: a derived client with no `defaultRequest` of its own inherits the parent's
  base (row 80).
- Not in the spec: the join rewrites a WebSocket call's scheme and may add `:443` (rows 61–62),
  and a call with no base at all sends to `http://localhost` (row 57).
