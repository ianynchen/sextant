# CP-41 — a value reassigned on one branch reaches its consumer with TWO producers

**Version scope.** Everything below is measured against **the JDK reporting
`JAVA_RUNTIME_VERSION` `21.0.12.1`** — the version the installation states in its own
`release` file, read by `probe.py` before it measures anything, never the value this harness
was handed. That is the version CI pins (`setup-java` 21) and the version every fixture is
built with. The first row of each pair is javac's behaviour and a later javac is free to
change how it allocates locals; the second is this repository's own extractor on that
bytecode. Both verdicts bound to `21.0.12.1` and to nothing wider.

**Why it was measured.** `OI-143`: `apolloconfig/apollo`'s HTTP wrapper does

```java
if (path.startsWith("/")) {
  path = path.substring(1);
}
doExecute(…, path, …);
```

and every one of 68 outgoing calls with a written path reaches `exchange` through that
method. Before capability 9.19 the extractor wrote the argument at the consuming call as
`{"kind": "unresolved"}` with no `source` — `MethodFlow.singleSource` reported a value with
exactly one producer and nothing otherwise — so the value walk had nothing to follow and
the 68 published as two unknown destinations. The spec
(`docs/superpowers/specs/2026-10-21-merged-values-design.md`) has the extractor write the
producers as CANDIDATES and choose none; this probe is what shows that javac leaves exactly
two, and what the extractor now writes for them.

## What the rows say

**Rows 1 and 3 — javac keeps a reassigned parameter in the slot it arrived in.** The one
`astore` in the fixture's `send` (and the first of Apollo's ten in `execute`) writes
`substring`'s result back into the parameter's own local. At the join after the `if`, that
slot's value therefore has two producing instructions — the parameter as it arrived and the
`substring` call — which is precisely the frame merge `SourceInterpreter` reports and
`singleSource` used to collapse.

**Rows 2 and 4 — the extractor now writes both, and chooses neither.** The argument at the
first consuming call is `{kind: merge, candidates: [parameter N, unresolved[source S]]}`:
the parameter marker first (it indexes nothing), then the call result WITH its `source`, so
the walk can look up call site `S` and read that its receiver is parameter `N` — the whole of
the root check in spec §3b. The fixture's consumer is the concat (`baseUrl + path`); Apollo's
first consumer is `uriTemplateHandler.expand(path, …)`, with the `doExecute` argument the
same merge one call later.

**The fixture is the production shape, measured side by side.** Row 2 and row 4 carry the
same two candidate kinds in the same order; the fixture differs from Apollo only in parameter
index (`send(HttpMethod, String path)` against `execute(HttpMethod, Env, String path, …)`).

## What this does NOT measure

* **What `substring` does.** Nothing here reads the call's semantics, and the design does
  not either (spec §3c, ruled 2026-10-21): a merge of `x` and a call on `x` resolves to `x`
  inexactly, whatever the call was.
* **A merge whose candidates share no root** — two literals on two branches. The extractor
  writes both candidates exactly as here; the walk answers `unresolved(non_enumerable)`,
  which is ruling 1 of the value-resolution design, unchanged. `MethodFlowTest` pins the
  fact's shape for that case.
* **Other compilers.** Kotlin's and ECJ's local allocation are not measured; a compiler that
  gave the reassignment a fresh slot would leave ONE producer at the consumer and no merge
  at all — a different fact, not a wrong one.
