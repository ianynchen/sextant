# CP-38 — what Spring Boot itself calls its path-prefix properties, per version

Spec `docs/superpowers/specs/2026-10-18-configured-path-prefixes-design.md` §3, whose table
pairs a path-prefix KEY with a framework and a version range. This is where those rows get
their evidence, and it comes from the framework's own bytes: Boot ships
`META-INF/spring-configuration-metadata.json` in its jars, naming every property it binds,
with deprecations and the properties that replaced them.

Re-run it rather than trusting this file:
`.venv/bin/python scripts/probes/cp38_boot_prefix_keys/keys.py`. Jars come from the local
Maven repository.

**Version scope.** Everything below is measured against **2.7.18**, **3.5.14** and **4.1.1** —
the versions whose jars this repository holds, each identified by the filename of the archive
the run opened. Nothing here is claimed for a version not in that list, and §3's table declares
rows only for what appears here.

## What the question is, exactly

The prefix a module serves its endpoints under comes from configuration, so something has to
know which KEY to read. Two earlier proposals rot: the build coordinate rots because Boot 4
renamed `spring-boot-starter-web` to `spring-boot-starter-webmvc`, and the bare key rots
because `server.context-path` became `server.servlet.context-path` in Boot 2. The ruling was
to record the key WITH its framework and version and pick per module — which needs the key
names measured per version, which is this.

## Observations

Generated by `scripts/probes/cp38_boot_prefix_keys/keys.py` — the figures are its stdout,
nothing is typed by hand. **Each column is the version the run printed for the jars it
actually opened, taken from each archive's own filename, not the version the argument asked
for**; a version absent from the repository prints no row at all, which is the CP-5 failure
this convention exists to prevent.

| property | 2.7.18 | 3.5.14 | 4.1.1 |
|---|---|---|---|
| `server.servlet.context-path` | `spring-boot-autoconfigure` | `spring-boot-autoconfigure` | **`spring-boot-web-server`** |
| `spring.mvc.servlet.path` | `spring-boot-autoconfigure` | `spring-boot-autoconfigure` | **`spring-boot-webmvc`** |
| `spring.webflux.base-path` | `spring-boot-autoconfigure` | `spring-boot-autoconfigure` | absent from the 37 read |
| `management.endpoints.web.base-path` | `spring-boot-actuator-autoconfigure` | `spring-boot-actuator-autoconfigure` | `spring-boot-actuator-autoconfigure` |
| `server.servlet.path` | deprecated → `spring.mvc.servlet.path` | deprecated → `spring.mvc.servlet.path` | deprecated → `spring.mvc.servlet.path` |
| `server.context-path` | absent from the 5 read | absent from the 5 read | absent from the 37 read |

Artifacts carrying property metadata, which is the denominator every absence above is bounded
by: **5** at 2.7.18 and 3.5.14, **37** at 4.1.1 — Boot 4 split the monolithic
`spring-boot-autoconfigure` into many artifacts, and the run lists which it read.

## What this settles

* **The NAMES are stable across 2.7.18 → 4.1.1**, for both keys §3's servlet row declares.
  What moved is the artifact that declares them.
* **A rename is recorded by the framework itself.** `server.servlet.path` carries
  `deprecation.replacement: spring.mvc.servlet.path` at all three versions, so the jar states
  both that the old spelling is dead and what took its place.
* **`server.context-path` is absent at all three**, consistent with it being Boot 1's spelling
  — but no Boot 1 jar is in this repository, so that is the absence of evidence for the old
  name and not evidence of its form. §3 declares no Boot 1 row for exactly this reason.

## What it does NOT settle

**`spring.webflux.base-path` is not measured at 4.1.1.** It is absent from the 37 artifacts
read, and `spring-boot-webflux` is not among them — the jar is not in this repository. Boot 4
demonstrably moved the MVC property into `spring-boot-webmvc`, so the parallel guess is that
the reactive one moved into `spring-boot-webflux`; that is an inference and this probe does not
make it. §3's reactive row is therefore bounded to 2.7.18 and 3.5.14, and a 4.x reactive module
is outside what the table was measured on until someone runs this with that jar present.
