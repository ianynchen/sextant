# CP-32 — the shipped listener annotations' own attributes: every element and its `AnnotationDefault`, and what each framework's own post-processor does with it

**Question.** `docs/superpowers/specs/2026-09-22-temporal-and-eventbus-design.md` §2e applies
Task 4's `metadata_from` key to the five listener catalogs that were already shipping, which
is **the only change in this plan that moves existing output**. §2e's own criterion is
stated so the list is not open-ended — *an attribute a peer would care about*, whether and
how a message reaches this handler — and the brief
(`.superpowers/sdd/2026-09-22-temporal-and-eventbus/task-9-brief.md`) asks this probe for
three readings per candidate attribute, on each framework, **before a catalog line is
written**: its declared type, its `AnnotationDefault`, and **what the framework's own
post-processor does with it**, so that a `metadata_from` entry's `kind` names what the
framework MEANS rather than what the attribute is called. Q1–Q5 are the element rows, Q6–Q10
the post-processor rows, Q11 the fixture rows (CP-27's row 16 / CP-30's and CP-31's Q9
applied here): which uses the committed fixtures' own compiled classes actually carry, and
therefore which shipped endpoints a `metadata_from` line moves.

**THREE ROWS CAME BACK DIFFERENT FROM WHAT THE CRITERION ASSUMED, AND THEY CHANGED THE LIST
RATHER THAN THE PROBE (GUIDELINES §1.1).**

1. **Micronaut's `groupId` has a second name, and it is the one most declarations use.**
   Q4a: `io.micronaut.configuration.kafka.annotation.KafkaListener` declares `value()` and
   `groupId()` as `@AliasFor` one another. `@KafkaListener("orders")` writes `value` into the
   class file and `@KafkaListener(groupId = "orders")` writes `groupId`, and Micronaut's own
   metadata layer resolves both to the group id (Q9 reads `AnnotationValue.stringValue` of
   `"groupId"` off metadata `@AliasFor` has already merged — javac has not). A catalog line
   naming only `groupId` would silently miss every declaration written the short way.
   `micronaut-kafka.yml` therefore carries TWO entries onto one `kind`.
2. **Micronaut JMS's selector is called `messageSelector`, and it sits on a different
   declaration.** Q5b/Q5c: `messageSelector(): String`, default `""`, on
   `io.micronaut.jms.annotations.Queue` and `...Topic` — the METHOD annotations — not on the
   class-level `@JMSListener`, which declares only `value`, `successHandlers` and
   `errorHandlers` (Q5a). Q10 reads the framework's own
   `AnnotationValue.get("messageSelector", String.class)` inside
   `AbstractJMSListenerMethodProcessor`. A probe that had looked for `selector` would have
   found nothing and reported the attribute absent.
3. **Micronaut JMS declares no durable-subscription attribute at all.** Q5a/Q5b/Q5c list
   every element of all three annotations: there is no `subscription`, no `durable`, no
   `sharedSubscription`. §2e's `subscription` row therefore applies to `spring-jms.yml` alone,
   and `micronaut-jms.yml` says so in words rather than leaving the absence to be read as an
   oversight.

**A fourth reading changed a `kind` word rather than the list.** §2e's table maps Spring
AMQP's `exclusive` to `kind: delivery`. Q3a measures what the attribute is —
`exclusive(): boolean`, default `false` — and Q8 measures what the framework does with it:
`MethodRabbitListenerEndpoint.setExclusive(Z)`, this consumer claims the queue exclusively.
`delivery` + `true` is ambiguous (true of WHAT?) while `exclusive` + `true` states the fact,
which is the same reading Task 8 already made when `quarkus-consume-event.yml` shipped
`kind: local` where §2e's table said `delivery`. The word used is `exclusive`, for that
precedent's reason and cited to this row.

**And one version in the brief does not exist.** The brief and §6 name "spring-jms 3.1.4".
There is no such artifact: `spring-jms` is versioned with Spring Framework, and
`spring-jms.yml`'s own `measured:` rows already cite **6.1.6** and 7.0.9. Every jar below is
read at a version the catalog that reads it already claims, because a `measured:` row may
cite no other.

**What this probe does not settle.** Nothing was run; every cell is a `javap` read of a class
file in one of five jars, or of a committed fixture's own compiled classes. It measures the
compiled surface of the versions named below — the LOWER version of each catalog's own
`measured:` pair, not both — so an attribute added, removed or re-defaulted at spring-kafka
4.1.1, spring-jms 7.0.9, spring-rabbit 4.1.1, micronaut-jms 4.5.0 or any Micronaut Kafka
other than 5.6.0 is outside it. Q6–Q10 dump every matching method's FULL instruction body
rather than a hand-picked excerpt, so nothing that disagreed with a prediction could have
been filtered out before a reader sees it; Q1–Q5 list EVERY element the annotation declares
rather than the ones a catalog reads, which is how findings 1–3 were found at all. Q1–Q5 read
the `AnnotationDefault` recorded on the annotation TYPE and say nothing about what any
particular USE carries — Q11 is the row that reads uses. Nothing here measures the
resolve-layer rules, any framework's runtime behaviour, or the property files and container
factories that also decide a consumer group.

**Version scope (§5.4).** `org.springframework.kafka:spring-kafka` **3.1.4**,
`org.springframework:spring-jms` **6.1.6**, `org.springframework.amqp:spring-rabbit`
**3.1.4**, `io.micronaut.kafka:micronaut-kafka` **5.6.0**,
`io.micronaut.jms:micronaut-jms-core` **4.2.0**. Every one of those five archives states an
`Implementation-Version` in its own manifest, and `probe.py` reads that value out of the
archive it opened and ABORTS when it disagrees with the coordinate `run.sh` requested — so,
like CP-31 and unlike CP-30, no SHA-1 fallback is reached here and no column is labelled with
a parameter. Two artifacts report the same version (spring-kafka and spring-rabbit are both
3.1.4) and share a header column; each row still names its own artifact. `fixtures/orders-service`
and `fixtures/orders-micronaut` carry no manifest: Q11's cells are filed under the class-file
version `javap -v` reports for them, the one identity a compiled class states about itself.

**How to run.** `JAVA_HOME=<jdk> PATH=$JAVA_HOME/bin:$PATH bash
scripts/probes/cp32_listener_attributes/run.sh`. It resolves the five jars into `~/.m2`
(Maven and network only if one is missing — all five were already present), compiles the two
fixtures offline, then runs `probe.py`, which reads each jar's `Implementation-Version` off
its own manifest and prints the table below. Needs a JDK for `javap` and Maven for the
`dependency:get` fallback and the fixtures' compiles. Not a test: nothing in the suite runs
it.

## Verdicts

**Q1a / spring-kafka 3.1.4 — `groupId` is a `String` defaulting to `""`, and the consumer
group is NOT read from it alone.** `@KafkaListener` declares 20 elements. The candidate is
`groupId()Ljava/lang/String;` with `AnnotationDefault` `s#10 = ""`. Beside it sit
`id()` (default `""`), `idIsGroup()Z` (default **`true`**) and `containerGroup()` (default
`""`) — three neighbours a reader has to tell apart, and Q6 is what tells them apart.
`@Target({TYPE, METHOD, ANNOTATION_TYPE})` and `@Repeatable(KafkaListeners.class)` are the
two facts the catalog already encodes (`class_level: sibling`, `container:`); they matter
here because a class-level use is a second declaration site and a repeated use reaches the
class file only inside its container.

**Q6 ★ / spring-kafka 3.1.4 — `getEndpointGroupId` reads `groupId` first and falls back to
the `id`.** The whole body, and it is the only method in the class that references
`KafkaListener.groupId:` at all: offset 3 calls `groupId()`, offset 8 gates it through
`StringUtils.hasText`, and only past that gate does offset 24 call
`resolveExpressionAsString(groupId, "groupId")` and store the result. Offsets 28–54 are the
other branch: where nothing was stored, `idIsGroup()` and `hasText(id())` together make the
already-resolved **id** the group. **Two consequences are recorded rather than encoded.**
(a) There is no `absent_value` to state: an absent `groupId` does not mean a measured
default, it means *the id, or the container factory's group* — a value that is not on this
declaration at all. Silence is the honest answer, so `spring-kafka.yml` declares none.
(b) `resolveExpressionAsString` means a written value may be a `${…}` placeholder OR a
`#{…}` SpEL expression. The placeholder is carried verbatim at `unresolved`, which is the
documented rule; the SpEL form is **dropped**, because `endpoint_attributes._text` asks
`names_a_type`, and that predicate is `'#' in value` (`domain/symbols.py`). A miss rather
than a wrong row, which is the direction NFR-2 asks for — and the reason this write-up
carries a correction into `docs/components/D02-catalog-schema.md` §2l, which stated the
`#`-drop's cost nowhere.

**Q1b / spring-kafka 3.1.4 — `@KafkaHandler` declares `isDefault()Z` and nothing else.** No
qualifying attribute of its own, which is why a `@KafkaHandler` endpoint's consumer group can
only come from the class-level `@KafkaListener` — exactly the enclosing-type read
`endpoint_attributes._uses_by_annotation` performs, and exactly why it performs it.

**Q2a / spring-jms 6.1.6 — `selector` and `subscription` are both `String`, both defaulting
to `""`.** `@JmsListener` declares six elements: `id`, `containerFactory`, `destination`
(the only one with **no** `AnnotationDefault` — it is required), `subscription`, `selector`
and `concurrency`. There is no seventh candidate and no `exclusive`-like boolean.
`@Target({METHOD, ANNOTATION_TYPE})`: no class-level use exists, so for this catalog the
enclosing-type half of the nearest-wins read can never fire.

**Q7a, Q7b ★ / spring-jms 6.1.6 — the post-processor sets both, each behind the same
`hasText` gate, each through the same placeholder resolution.** One method references either
attribute — `processJmsListener` — and its whole body shows the pair at offsets 87–113 and
114–140: `selector()` → `hasText` → `resolve(…)` → `MethodJmsListenerEndpoint.setSelector`;
`subscription()` → `hasText` → `resolve(…)` → `setSubscription`. The framework MEANS by
`selector` a JMS message selector applied at the consumer, and by `subscription` the name of
a durable subscription, so `kind: selector` and `kind: subscription` name what the framework
means and the attribute's own name coincides with it. The `""` default is the same
"absence, not a value" case as Kafka's: an empty string writes no row (D02 §2l), and no
`absent_value` is declared. `resolve(…)` puts a JMS selector in the same SpEL/placeholder
position as a Kafka group — and a JMS selector is, of every value this key reads, the one
most likely to quote a `#` in its own expression text, which is the second half of the §2l
correction.

**Q3a / spring-rabbit 3.1.4 — `exclusive()` is a genuine `boolean`, default `false`, and it
is one of two `exclusive`s.** `@RabbitListener` declares 20 elements;
`exclusive()Z -> Z#18 = false` is the candidate. Q3c reads the NESTED
`org.springframework.amqp.rabbit.annotation.Queue`, which declares an `exclusive()` of its
own — `Ljava/lang/String;`, default `"false"` — meaning something else entirely (the queue
being DECLARED is exclusive to its connection, not this consumer's claim on it). The two
never collide in practice because a `metadata_from` entry names the annotation as well as
the attribute, but the collision is why it must.

**Q8 ★ / spring-rabbit 3.1.4 — `processListener` sets it unconditionally.** The whole body of
the one method that references `RabbitListener.exclusive:`: offset 256 calls `exclusive()`
and offset 261 passes it straight to `MethodRabbitListenerEndpoint.setExclusive(Z)` — no
`hasText`, no expression resolution, no gate, because a `boolean` has no empty form. So the
value a declaration writes IS what the framework acts on, and `kind: exclusive` names it.
**No `absent_value`, and the reason is a distinction rather than an omission.** The default
was measured (`false`) and could be stated; it is not, because `exclusive = false` is the
state of every ordinary consumer on every queue, and a row on every Rabbit endpoint saying so
states nothing a peer acts on. Compare `quarkus-consume-event.yml`, which DOES declare
`absent_value: "true"`: there the default is the peer-relevant value (a local-only consumer
is invisible to the rest of the cluster), so silence would have hidden the fact. State the
default when the DEFAULT is what a peer would act on.

**Q4a ★ / micronaut-kafka 5.6.0 — `value` and `groupId` are `@AliasFor` one another.** The
headline finding. Both are `String`, both default `""`, and each carries
`io.micronaut.context.annotation.AliasFor(member=…)` naming the other. javac writes whichever
the source wrote; Micronaut's own annotation-metadata layer merges them. Also read here, and
recorded as a stated boundary rather than encoded: `uniqueGroupId()Z`, default `false`.

**Q9 ★ / micronaut-kafka 5.6.0 — the group is `AnnotationValue.stringValue("groupId")`,
defaulted to the bean's class name, and `uniqueGroupId` appends a UUID to it.** The whole
body of the one `KafkaConsumerProcessor` method that loads the string `groupId`: offsets
56–85 read `stringValue("groupId")`, `filter` a predicate over it and `orElseGet` a supplier
built from the bean type (the class name is the fallback group); offsets 146–167 test
`isTrue("uniqueGroupId")` and, where true,
`makeConcatWithConstants(group, UUID.randomUUID())`. Two things follow. The `AnnotationValue`
being read is Micronaut's MERGED metadata, which is why `value` is as much the group id as
`groupId` is — finding 1, measured rather than assumed. And a declaration that also writes
`uniqueGroupId = true` joins `<declared>-<uuid>` rather than `<declared>`; the recorded value
is then a prefix of the real group. That is a stated boundary in `micronaut-kafka.yml`, not a
condition in the entry: `metadata_from` has no `unless`, and the declared value is still the
group a reader would look for.

**Q4b / micronaut-kafka 5.6.0 — `@Topic` declares `value()[Ljava/lang/String;` and
`patterns()`, and no qualifying attribute.** The handler's own annotation carries nothing
this key reads, which is what makes the enclosing-type read load-bearing for this catalog:
the group sits on the class and the row's handler is the method.

**Q5a / micronaut-jms 4.2.0 — `@JMSListener` declares `value`, `successHandlers`,
`errorHandlers`, and `@Target({TYPE})`.** No selector, no subscription, no exclusivity. The
class-level annotation this catalog gates on carries nothing a peer would care about beyond
the connection-factory bean name `micronaut-jms.yml` already reads as its `protocol_hint`.

**Q5b, Q5c ★ / micronaut-jms 4.2.0 — the selector is `messageSelector`, on `@Queue` and on
`@Topic`.** Both annotations declare an identical element list: `value` (`@AliasFor`
`MessageMapping.value`, no default — required), `serializer`, `acknowledgeMode()I` (default
`1`), `transacted()Z` (default `false`), **`messageSelector()Ljava/lang/String;` (default
`""`)**, `successHandlers`, `errorHandlers`. Findings 2 and 3 together: the name differs from
Spring's, the site is the METHOD rather than the class, and there is no durable-subscription
element on any of the three annotations.

**Q10 ★ / micronaut-jms 4.2.0 — `AbstractJMSListenerMethodProcessor` reads it as an
`Optional` and carries it into the listener registration.** The whole body of the one method
that loads the string `messageSelector`: offsets 51–60 call
`AnnotationValue.get("messageSelector", String.class)` and store the `Optional`, beside
`getRequiredValue` reads of the destination, `acknowledgeMode` and `transacted`. The
framework MEANS a JMS message selector, so `kind: selector` — the same word `spring-jms.yml`
uses for the same wire fact under a different attribute name, which is the whole point of
naming the kind after the meaning.

**Q11a / `fixtures/orders-service` — NOT ONE SPRING DECLARATION IN THE REPOSITORY WRITES A
QUALIFYING ATTRIBUTE.** Every `@KafkaListener`, `@JmsListener` and `@KafkaHandler` use the
fixture carries is listed with the elements it writes, and they are `topics`, `topicPattern`,
`destination`, `batch` and `isDefault` — no `groupId`, no `selector`, no `subscription`. The
fixture carries no `@RabbitListener` at all. So the three Spring catalogs' new
`metadata_from` blocks derive **nothing** from this fixture, and no `endpoint_metadata`
assertion over it moves.

**Q11b ★ / `fixtures/orders-micronaut` — EXACTLY ONE declaration moves.**
`com.acme.mn.OrderMessaging$KafkaConsumer` carries
`io.micronaut.configuration.kafka.annotation.KafkaListener(groupId="orders")` **on the class
itself**, and its one handler `onPlaced` carries `@Topic(value=["mn.orders.placed"])`. Every
other use in the fixture — three `@JMSListener(value=…)` on classes, five `@Queue(value=…)`
and two `@Topic(value=…)` on methods — writes only the element the catalog already reads as
a destination or a connection-factory name. So the entire moved output of §2e across this
repository is ONE `endpoint_metadata` row: `consumer_group = orders` on the inbound `kafka`
endpoint `mn.orders.placed`, reached through the enclosing-type half of the nearest-wins read
because the handler carries no `@KafkaListener` of its own. **That the moved set is one row
is a fact about the fixtures, not a claim about the catalogs**: each of the five entries is
measured above against the framework that honours it, and a repository that writes
`@JmsListener(selector = …)` gets its row on the same line.
