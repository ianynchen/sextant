# CP-44 — where Spring evaluates a condition on a bean, and what `@ConditionalOnMissingBean` checks

**Version scope.** Everything below is measured against **`spring-context`, `spring-beans` and
`spring-web` as their own manifests state them** (`Implementation-Version` — `7.0.9` for all
three when this record was made) and **`spring-boot-autoconfigure` as its own manifest states
it** (`4.1.1`), read by `probe.py` out of the jars in the local Maven repository — never the
directory name this harness found them under, which is the CP-5 failure the convention exists
to prevent. The rules are platform behaviour of the Spring Framework (`7.0.9`) and Spring Boot
(`4.1.1`) and a later release is free to change any of them, so the verdicts here bound to the
versions in the table and to nothing wider.

**Why it was measured.** The bean-model vocabulary of `conditional-beans` (spec
`docs/superpowers/specs/2026-10-22-conditional-beans-design.md` §2a, §2b) says which classes
are beans and which annotations Spring consults when it registers each one: a scanned class
its own, a `@Bean` method its own AND its configuration class's, a class merely constructed
inside a `@Bean` body the factory method's. That table was written from the documentation;
this probe reads it off the bytecode before anything is built on it. CP-42 (`@Profile`) and
CP-43 (`@ConditionalOnProperty`) stand and are not repeated.

## What the rows say

**Row 1 — an unannotated use is deduced from the return type, and only on a `@Bean` method.**
`Spec.<init>` extracts `value`/`type`, `name` and `annotation` first and calls
`deducedBeanType` only when all three sets are empty. `deducedBeanType` acts on a
`MethodMetadata` that carries `@Bean`: `getReturnType` resolves the method's declared return
type (`getMethodReturnType` -> `ResolvableType.resolve`) and, when `isParameterizedContainer`
holds, its first generic (`getGeneric`). Any other target — a class — deduces the empty set
and `validate` refuses it with an `IllegalStateException`. So the type an unannotated
`@ConditionalOnMissingBean` on a `@Bean` method checks is the method's return type, which is
the class this analysis already knows from the method's signature, and an unannotated use on
a class never registers at all (the framework fails first).

**Row 2 — `value` and `type` are one set of types; `name` and `annotation` are separate
criteria.** The type criterion is looked up with `getBeanDefinitionsForType`, the name
criterion with `containsBean`, the annotation criterion with `getBeanDefinitionsForAnnotation`.
`@ConditionalOnBean` holds when `isAllMatched` — no listed criterion is left unmatched —
and `@ConditionalOnMissingBean` fails when `isAnyMatched` — some listed criterion matched. A
use that lists a type AND a name therefore needs both for `@ConditionalOnBean` and is defeated
by either for `@ConditionalOnMissingBean`.

**Row 3 — the search is against the definitions registered at the moment the condition
runs.** `OnBeanCondition` is a `ConfigurationCondition` at phase `REGISTER_BEAN`;
`ConditionEvaluator.shouldSkip` only runs a condition whose phase is the one it was handed, so
the parser's `PARSE_CONFIGURATION` calls pass over it and the reader's `REGISTER_BEAN` calls
run it. Inside the reader the condition of a `@Bean` method is judged BEFORE that method's own
definition is registered (offset 26 against 758), against `getBeanNamesForType` called with `includeNonSingletons = true` and
`allowEagerInit = false`, which reads `beanDefinitionNames` (what the registry holds so far)
and `manualSingletonNames`, and instantiates nothing. A
`@ConditionalOnMissingBean` default is therefore decided by what has been registered before
it, which is an order: the answer for a module read from its own beans alone can differ from
the container's when a library or the processing order registers a competitor later. This is
why spec decision 2 publishes those verdicts at `partial`.

**Row 4 — five call sites, and none takes anything a method body constructs.**
`ConditionEvaluator` is package-private, so the call sites are exactly those of its own
package. They hand it (a) the metadata of a class the scanner found, (b) the metadata of a
class registered programmatically, (c) the metadata of a configuration class — at parse time
(`PARSE_CONFIGURATION`, so imported and member configuration classes are reached through
`processImports` / `processMemberClasses` / `parse`) and again, through the tracking wrapper,
when the reader registers it (`REGISTER_BEAN`), (d) the metadata of a `@Bean` METHOD. When the
configuration class is skipped `loadBeanDefinitionsForConfigurationClass` returns before it
reads `getBeanMethods`, so a skipped configuration registers none of its `@Bean`s — and an
imported configuration class is skipped only if every importer is (`isImported` ->
`getImportedBy`). A `@Bean` method is therefore conditioned by its own annotations AND its
configuration class's, and a component-scanned class by its own, exactly as the spec's §2a
table states. No call site is handed an object a `@Bean` body creates: the class a method
merely CONSTRUCTS is never an argument, which is why only the factory method's conditions
apply to it.

**Row 5 — the stereotype set.** The scanner's default include filter is an
`AnnotationTypeFilter` for `@Component`, which matches meta-annotations; each of the eight
annotations the bean model lists reaches `@Component` itself or through the annotation it is
built on (`@RestController` through `@Controller`, `@RestControllerAdvice` through
`@ControllerAdvice`). This row is an addition to the four the plan named, for the model's
`stereotypes` list.

## What this does NOT measure

* **That the order configuration classes are processed in is the order the module's own
  facts imply.** Row 3 shows the search reads what is registered when it runs; the order the
  container visits configuration classes in (parse order, `@Order`, imports) is not read here.
  A competing bean registered later, or by a library, is the stated reason those verdicts are
  `partial`.
* **Auto-configuration.** Spring Boot also filters auto-configuration CLASSES with
  `OnBeanCondition.getOutcomes` before registration; those are library classes and the module's
  own beans are not auto-configurations, so the probe does not read that path.
* **That a class constructed inside a `@Bean` body is never registered.** Row 4 shows no call
  site is handed one; that `new X()` in a method body is outside the container is the JVM's
  and the container's model, not something a class file of this jar states.
* **Generic return types.** Row 1 reads the call chain `getReturnType` runs; which type
  results for a return type with unresolved generics is not exercised.
* **Conditions outside the package.** Another framework's container (Micronaut, Quarkus) has
  its own registration points; this probe is Spring's.
