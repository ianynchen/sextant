# CP-55 — Quartz 2.5.x builders, Scheduler overloads and `QuartzJobBean`, measured

**Version scope.** Everything below is measured against Quartz **2.5.1** (`org.quartz-scheduler:quartz`
**as its own manifest states it**, `Implementation-Version` 2.5.1) and, for `QuartzJobBean`, spring-context-support
**7.0.1** (`org.springframework:spring-context-support`, `Implementation-Version` 7.0.1). Those are the
versions Spring Boot 4.0.0's `spring-boot-starter-quartz` manages (`quartz.version` 2.5.1,
`spring-framework.version` 7.0.1). The probe module is compiled by javac 21 (class file major version 65).
`probe.py` reads each jar out of the local Maven repository and takes the version from the jar,
never from the directory name the harness found it under (the CP-5 failure the convention exists
to prevent), and the JVM that loaded the same classes has to report the same version or the run
aborts. These are shapes of Quartz 2.5.1, spring-context-support 7.0.1 and javac 21's output;
Quartz 2.3.x and earlier, a later Quartz or Spring Framework, and a different compiler are free to
change any of them, so the verdicts bound to the versions in the table and to nothing wider.

**Why it was measured.** The Quartz design (spec `docs/superpowers/specs/2026-10-28-quartz-design.md`)
gives the Quartz catalog data to write: which builder factories start a job or a trigger chain, which
`Scheduler` calls register one, which group a key without one lands in, what `QuartzJobBean`'s
`execute` calls, and how javac builds the `Integer...` arguments of the weekday builders. Every one
rests on a fact about Quartz's or Spring's bytecode, or javac's output, that nobody had written
down. This record is what the Quartz catalog cites in its `measured:` block.

**What this probe does not settle.** It measures what the libraries and javac produce for a probe
module of our own; it reads no downloaded project and starts no scheduler (the module is compiled,
and its `main` only builds three keys and asks the two jars' packages their version). The six builder
classes and the three `Scheduler` method names are listed in full; the rest of `Scheduler`
(`triggerJob`, `addJob`, `unscheduleJob`, `pauseJob`, ...) is not enumerated, and `QuartzJobBean` is
measured only for `execute`, not for the Spring beans that wire jobs (`JobDetailFactoryBean`,
`SimpleTriggerFactoryBean`, `CronTriggerFactoryBean`, `SchedulerFactoryBean`). The fluent instance
methods of the builders (`withIdentity`, `withSchedule`, `forJob`, ...) are not enumerated here.
How real corpora use these calls is the builder's fixture and corpus work, not this record.

**How to run.** `JAVA_HOME=<jdk 21> bash scripts/probes/cp55_quartz_shapes/run.sh`. It
compiles `scripts/probes/cp55_quartz_shapes/module/` with Maven after a `clean` (so no cell
can come from a stale build), asks Maven for the module's classpath, then runs `probe.py`, which
prints the table below. Needs a JDK 21 (for `javap` and `java`), Maven, and network on the first
run only (Quartz 2.5.1 and spring-context-support 7.0.1 are cached in `~/.m2` afterwards). Not a
test: nothing in the suite runs it.

## What the rows say

Letters (a)-(f) are the questions the probe was written to answer. Each verdict names the spec
section (`docs/superpowers/specs/2026-10-28-quartz-design.md`) it supports.

**(a) Rows 1-6 — the factories, by descriptor.** `JobBuilder` has two: `newJob()` and
`newJob(Class)`. `TriggerBuilder` has one, `newTrigger()`; `CalendarIntervalScheduleBuilder` and
`DailyTimeIntervalScheduleBuilder` have one each, `calendarIntervalSchedule()` and
`dailyTimeIntervalSchedule()`. `CronScheduleBuilder` has seven (`cronSchedule(String)`,
`cronSchedule(CronExpression)`, `cronScheduleNonvalidatedExpression(String)`,
`dailyAtHourAndMinute(II)`, `atHourAndMinuteOnGivenDaysOfWeek(II[Integer)`,
`weeklyOnDayAndHourAndMinute(III)`, `monthlyOnDayAndHourAndMinute(III)`), and
`SimpleScheduleBuilder` thirteen (`simpleSchedule()` and the
`repeat{Secondly,Minutely,Hourly}{Forever,ForTotalCount}` family; the `Forever` ones take zero or
one int, the `ForTotalCount` ones one or two). A name alone is not enough where it has overloads:
the descriptor tells `cronSchedule(String)` (an expression to read) from
`cronSchedule(CronExpression)` (an object to follow). Supports the builder-chain rows of the design.

**(b) Rows 7-9 and 23 — the Scheduler overloads, and how a call to each compiles.** `scheduleJob`
has three: `(JobDetail, Trigger)` and `(Trigger)` both return `Date`, and `(JobDetail, Set,
boolean)` returns `void`; `scheduleJobs` has one, `(Map, boolean)`; `rescheduleJob` has one,
`(TriggerKey, Trigger)`. `Scheduler` is an interface, so every call is `invokeinterface` on
`org/quartz/Scheduler` (row 23), and the trigger argument sits at a different position in each form
(argument 1 of the two-argument form, argument 0 of the one-argument form, a `Set` or a `Map` of
triggers in the others), so the overload is chosen by descriptor, not by name or arity. Supports the
dispatcher rows of the design.

**(c) Rows 10-18 — the default group is declared once, on `Key`.** `DEFAULT_GROUP` is a `public
static final String` on `org.quartz.utils.Key`, `"DEFAULT"`, and neither `JobKey` nor `TriggerKey`
declares one (row 10); javac reads `JobKey.DEFAULT_GROUP` and `TriggerKey.DEFAULT_GROUP` as the
inlined string `DEFAULT` (rows 14-15). The factories `jobKey(String)` and `triggerKey(String)` pass
a **null** group (`aconst_null`) to the constructor (rows 11-12), and `Key`'s constructor replaces a
null group with `"DEFAULT"` and rejects a null name (row 13), which Quartz itself confirms for three
forms (rows 16-18). So a key without a group has the group `DEFAULT` for jobs and triggers alike,
and the group is absent from the bytecode at the call site. Supports the trigger-name-as-identity
and default-group rules.

**(d) Row 19 — `QuartzJobBean.execute` calls `executeInternal` on its own class.** The call is
`invokevirtual executeInternal:(Lorg/quartz/JobExecutionContext;)V` with **no owner in the
constant-pool comment** (javap prints a call on the class's own methods that way), after `execute`
has copied the scheduler context and the merged job data map onto the bean's properties through a
`BeanWrapper`. A subclass is therefore found as the class that overrides
`executeInternal(JobExecutionContext)`, and the job data entries reach it through setters, not through
the call. Supports the job-entry rule.

**(e) Rows 20-21 — the `Integer...` arguments are built inline, from `int` constants.**
`onDaysOfTheWeek(Calendar.TUESDAY, Calendar.THURSDAY)` compiles to `iconst_2; anewarray
java/lang/Integer`, then for each element `dup; iconst_<index>; iconst_<value>; invokestatic
Integer.valueOf:(I)Ljava/lang/Integer; aastore`, with the constants 3 and 5 (javac folds
`Calendar.TUESDAY` and `THURSDAY`), and then the `invokevirtual`.
`atHourAndMinuteOnGivenDaysOfWeek(3, 0, 1, 2)` pushes the two leading ints (3, 0) first, then builds
a two-element `Integer` array for the days 1 and 2 the same way, then `invokestatic`. A reader that
follows the array has to follow `anewarray`, `dup`, an index, a boxed value, `aastore`. Supports the
weekday-builder rows.

**(f) Row 22 — the eight boxing methods, as javac names them.** `java/lang/Boolean.valueOf:(Z)`,
`Byte.valueOf:(B)`, `Character.valueOf:(C)`, `Short.valueOf:(S)`, `Integer.valueOf:(I)`,
`Long.valueOf:(J)`, `Float.valueOf:(F)` and `Double.valueOf:(D)`, each returning its own wrapper
(`Ljava/lang/<Wrapper>;`). A reader that sees through boxing names exactly these eight. Supports the
value-walk rows that must see through a boxed constant.
