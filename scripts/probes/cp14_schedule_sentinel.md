# CP-14 — the value a `@Scheduled` declaration uses to say *never*

**Question.** `docs/open-issues.md`'s **`OI-2`** (Major) records that
`spring-scheduling.yml` "treats no cron value as the framework's 'never
schedule this' sentinel, because no probe has measured which value the
framework so reads and encoding one from memory is what §8.1 forbids. So a
schedule the framework will never run publishes a `scheduled_work` row saying
it does." That row also says why the case is not excused by §8.2: **a disable
sentinel is not deployment-overridable** — it is a constant compiled into the
caller's own class file, so misreading it is misreading code rather than
missing configuration.

Five questions, one reading of one class pair:

| # | what it asks | why the catalog needs it |
|---|---|---|
| 1 | what `@Scheduled` declares — its compile-time constants, then its attributes | a framework naming its own disable value in the annotation's public API states a fact about the DECLARATION; the attribute list is the enumeration `triggers` was chosen from |
| 2 | which attribute the sentinel is compared against, and which registration the comparison stands in front of | a constant named `CRON_DISABLED` is a name, not a behaviour |
| 3 | every string comparison in the post-processor | the converse CP-10's table is criticised for never asking: is that value the ONLY absence, or does a fixed rate or delay have one too |
| 4 | every instruction between the `cron()` read and the comparison | whether reaching the sentinel still counts as having declared a schedule — which decides what a disabled cron BESIDE a live `fixedDelay` does |
| 5 | from the comparison to the first assertion that follows it | what reads the flag row 4 finds written, so the consequence is measured rather than inferred |

**What this probe does not settle, and the verdict must not be read past it.**
Nothing here was deployed. It records the instructions the post-processor
executes; it does not observe a container starting, a task firing, or a task
failing to fire. What it can say is which registration call each branch
reaches, and that is the fact `scheduled_work` publishes.

**Version scope (§5.4).** Read against **spring-context 6.1.6, 6.2.19 and
7.0.9**. Three minors rather than one, for CP-12's reason: a sentinel is a
version-scoped fact and one reading cannot say whether it is stable. 6.1.6 is
what `fixtures/orders-service/pom.xml` pins; 6.2.19 and 7.0.9 are the two later
generations, so the three columns span every Spring line this repository claims
to read. **Every verdict below is bounded by those three.**

**How to run.** `bash scripts/probes/cp14_schedule_sentinel/run.sh`. It resolves
each jar through Maven (network on the first run only, cached in `~/.m2`
afterwards) and asks `javap` the five questions. Needs a JDK and Maven. Not a
test: nothing in the suite runs it, and NFR-1's no-network rule governs the
suite rather than evidence gathering.

## Expectation table

| # | Under test | Expected |
|---|---|---|
| 1 | `@Scheduled`'s constants | a named disable constant, or none — either answer settles `OI-2` |

## Verdict

1. **`OI-2` is confirmed, and the sentinel is `@Scheduled.CRON_DISABLED`,
   whose value is `-`.** Row 1 reads it off the annotation's own class file at
   all three minors, byte-identical. It is a compile-time constant of the
   framework's public API, so a declaration writing it has written a fact this
   repository can see — which is precisely the line §8.2 draws: a deployment
   can overwrite a property placeholder and cannot overwrite a constant javac
   has already inlined into the caller.

2. **It withdraws exactly one registration, and `spring-scheduling.yml` must
   drop exactly one row.** Row 2 puts the comparison between the `cron()` read
   and `ScheduledTaskRegistrar.scheduleCronTask`, and shows it reaching no
   other `schedule*` call: the three that follow — `scheduleFixedDelayTask`,
   `scheduleFixedRateTask`, `scheduleOneTimeTask` — are each guarded by their
   own attribute's `isNegative` test and not by this one. So
   `@Scheduled(cron = "-")` registers NO task, and a `scheduled_work` row for
   it is work the framework will never do.

3. **It is the only sentinel, at all three minors.** Row 3 enumerates every
   string comparison in the post-processor and finds ONE. `fixedDelay`,
   `fixedRate` and their `String` twins have no disable value: they are
   withdrawn by being absent, which this catalog already derives nothing for.
   The new catalog key is therefore bounded to `cron` by measurement rather
   than by choice, and a second constant appearing at a later minor turns row 3
   into the finding rather than leaving it to anybody's memory.

4. **The comparison happens AFTER placeholder resolution, which bounds what we
   may claim about `${...}`.** Row 4's cell puts two
   `StringValueResolver.resolveStringValue` calls between the `cron()` read and
   the comparison, so a placeholder whose deployed value is `-` is disabled by
   the same rule. This repository does not resolve placeholders (§8.2) and must
   not start: `@Scheduled(cron = "${orders.sweep}")` stays `unresolved`, which
   is what it already was, and the row says so rather than claiming either
   answer.

5. **Reaching the sentinel still counts as having declared a schedule — so a
   disabled cron BESIDE a live rate is a declaration the container refuses.**
   Row 4 ends `... iconst_1 ; istore ; ldc_w String - ; aload ;
   String.equals`: the "a schedule was declared" flag is written BEFORE the
   comparison, for any non-empty cron including the sentinel. Row 5 carries the
   read: after `fixedDelay()` is found non-negative the flag is loaded, negated
   and passed to `Assert.isTrue`, which fails. So
   `@Scheduled(cron = "-", fixedDelay = 1000)` starts no task at all because
   the post-processor throws, while this repository would publish the
   `fixedDelay` row.

   **Its boundary, stated because the verdict must not be read past it.** The
   assertion's message is loaded from a local slot written at method entry, so
   no generated cell here carries its text; what rows 4 and 5 measure is that
   the flag is written before the comparison and read into a failing assertion
   after it. Nothing was deployed, so "the container refuses to start" is what
   those instructions do rather than what a run observed. That shape is
   **registered as `OI-34` rather than encoded**: it needs a rule about a
   DECLARATION as a whole, where every conjunct this style has is per
   attribute, and §8.1 rule 4 forbids deriving on half a rule.
