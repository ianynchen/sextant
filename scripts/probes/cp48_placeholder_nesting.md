# CP-48 — where a nested placeholder ends, and whether a default holding one is resolved

**Version scope.** Everything below is measured against **`spring-core` as its own manifest
states it** (`Implementation-Version` — `7.0.9` when this record was made), read by
`probe.py` out of the jar in the local Maven repository — never the directory name this
harness found it under, which is the CP-5 failure the convention exists to prevent. The rules
are platform behaviour of the Spring Framework (`7.0.9`) and a later release is free to change
any of them, so the verdicts here bound to the version in the table and to nothing wider.

**Why it was measured.** `resolve/config.py::substitute` is the project's one placeholder rule
(spec 2026-10-23-configured-schedules §3a): `resolve_config` substitutes configuration values
through it and `resolve/resolved_schedules.py` substitutes a `@Scheduled` expression. It
ended a placeholder at the FIRST closing delimiter, so `${missing:${a}}` read the inside
`missing:${a`, took the default `${a` and kept the trailing `}` — the literal `${a}` — and a
`${jobs.sweep.cron:${jobs.default.cron}}` schedule read as that literal in every environment
that sets no `jobs.sweep.cron` (final review of the branch, ruled 2026-10-23). Both readers'
values come from Spring's `PropertyPlaceholderHelper` — Boot's binder and the
`embeddedValueResolver` a `@Scheduled` attribute goes through — so how that parser finds a
placeholder's end and what it does with a default are read off the jar before the rule is
changed to match.

## What the rows say

**Rows 1–3 — a placeholder ends at the closer that balances it.** `PropertyPlaceholderHelper`
is a front for `PlaceholderParser`. Its end search starts after the opener and counts depth:
each `simplePrefix` it passes raises the count, each closer at a depth above zero lowers it
and is passed over, and the first closer at depth zero is the end. `simplePrefix` is not the
opener: for a closer with a well-known partner (`}` → `{`, `]` → `[`, `)` → `(`) and an opener
ending in that partner, it is the partner alone — so for `${…}` the count is of `{`, and a
bare brace inside a placeholder (`${k{x}:d}`) nests as `${` does. Otherwise it is the whole
opener.

**Row 4 — an opener with no end is text, and the scan goes on.** The opener is kept as
written and the search for the next opener resumes just after it, so in `${a ${b}` the first
opener is text and `${b}` is still substituted.

**Rows 5 and 6 — the inside is parsed again, and the separator splits text only.** A
placeholder's inside is itself parsed. With no placeholder in it, it splits at the FIRST
separator: the key before, the default the whole rest (`${k:a:b}` defaults to `a:b`). With one,
the inside is a sequence of text and placeholders: the first TEXT piece holding the separator
splits there, everything before it is the key (a placeholder there is part of the key's
name) and everything after — that piece's rest and every later piece — is the default. A
separator inside a nested placeholder never splits the outer one.

**Row 7 — a default holding a placeholder IS resolved.** `NestedPlaceholderPart.resolve`
resolves the key's parts, looks the resulting key up, and where it answers nothing resolves
the default's parts — through the same resolver. So
`${jobs.sweep.cron:${jobs.default.cron}}` is `jobs.sweep.cron`'s value where it is set and
`jobs.default.cron`'s where it is not; an inner placeholder that cannot be resolved either is
unresolvable in its turn, its own default applying first. A simple part's default holds no
placeholder (row 5), so it is returned as written.

**Row 8 — a cycle through a default is still a cycle.** A looked-up value holding a
placeholder is parsed and resolved with its key flagged visited until it is done; reaching a
flagged key again throws `Circular placeholder reference`. A default's placeholders are
resolved inside that chain, so `a: ${b:${a}}` with no `b` comes back to `a` and is a cycle.

## What is built from it

`substitute` (spec 2026-10-23-configured-schedules, final review) finds a placeholder's end
by rows 2–3, with the counted opener declared beside the delimiters as the config model's
`placeholders.nest` (`spring-web.yml`: `"{"`, `by:` this record) rather than derived from a
bracket table in the code; leaves an opener with no end as text and scans on (row 4); splits
key and default by rows 5–6; resolves a nested key and a default through the caller's own
lookup (row 7); and reports the cycle of row 8 as `placeholder_cycle`, as `resolve_config`'s
lookup already did.

## What this does NOT measure, and what is not built

* **Row 9 — a simple part first looks up its WHOLE inside.** For `${a:b}`,
  `SimplePlaceholderPart` asks for a property named `a:b` before it asks for `a`. Not built:
  it changes an answer only where a configuration declares a key spelled with the separator
  in it — not measured on the fixtures or the corpus; logged as OI-184.
* **Row 10 — the escape character.** `PlaceholderParser` honours an escape character before an
  opener and before a separator. Which character Boot's binder and the bean factory's
  embedded value resolver pass, if any, is a constructor argument this record does not read,
  so `substitute` does not model escaping; OI-184 with row 9.
* **An unresolvable placeholder in Boot's binder.** Whether a caller ignores an unresolvable
  placeholder (keeping its text) or fails is the caller's flag, not the parser's; `substitute`
  keeps answering such a value unresolved with its reason, which is this project's rule, not
  a claim about Spring's.
