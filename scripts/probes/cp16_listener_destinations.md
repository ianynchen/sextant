# CP-16 — which attributes of a listener annotation name a destination

**Question.** Three shipped catalogs — `spring-kafka.yml`, `spring-jms.yml` and
`spring-rabbit.yml` — each read a destination off a listener annotation, and
each states its rule as a `CHECKPOINT FACT` comment with no version and no
committed evidence. All three are entries in
`tests/architecture/test_catalog_measurement_coverage.py::_NOT_MEASURED_YET`,
and `docs/principles-sweep-2026-09-05.md` §6.2 ranks them together at **rank 7**
of its probe backlog: *"four listener catalogs whose attribute rules are
checkpoint notes with no version"*.

One reading answers the same four questions at all three sites:

| # | what it asks | why the catalogs need it |
|---|---|---|
| 1 | every attribute the listener annotation declares, with its TYPE | each catalog's `path_from` is an alias set chosen out of this list, and an alias set is only as trustworthy as the enumeration it was chosen from |
| 2 | `@Target` and `@Repeatable` on it | `@Target` bounds where a declaration may sit; `@Repeatable` names the CONTAINER javac folds two uses on one method into — a class file then carries the container and NOT the annotation, so a catalog that does not name it sees nothing at all |
| 3 | what the sibling polymorphic-handler annotation declares | `spring-kafka.yml` and `spring-rabbit.yml` both claim theirs carries no address and reaches one only through the class-level listener |
| 4 | how the post-processor FINDS the annotation, and which of its attributes it reads | the attribute set is the destination claim; the search is whether a meta-annotated, inherited or REPEATED declaration is found at all |

**What this probe does not settle, and the verdict must not be read past it.**
(a) **Nothing was deployed.** It records which attributes the post-processor
reads and which endpoint setter each feeds; it does not observe a broker
delivering a message. (b) **The SEMANTICS of Spring's two annotation-search
entry points are not measured here.** Row 4 records which method is called —
`AnnotatedElementUtils.findMergedAnnotation`,
`AnnotatedElementUtils.getMergedRepeatableAnnotations`, or
`MergedAnnotations.from(element, TYPE_HIERARCHY).stream(…)` — and only the
third carries its search strategy as a constant this probe can read. What the
other two search is Spring's own contract and stays unmeasured; the verdicts
below say so rather than filling it in. (c) **`spring-rabbit` 4.1.1 moved its
search into a superclass in a DIFFERENT artifact** (`spring-amqp`'s
`AbstractListenerAnnotationBeanPostProcessor`), which this probe does not open;
the cell says so in the framework's own words rather than printing nothing,
because an empty cell reads as "the rule is gone" — the CP-7 failure one class
up.

**Version scope (§5.4).** Read against **spring-kafka 3.1.4 and 4.1.1,
spring-jms 6.1.6 and 7.0.9, and spring-rabbit 3.1.4 and 4.1.1**. Two minors per
framework, for CP-12's reason: an attribute set is a version-scoped fact and one
reading cannot say whether it is stable. The lower column of each pair is the
version the shipped catalog's own comment names or the fixture resolves; the
upper is the current generation, so each pair spans a major boundary rather than
two patch releases. **Every verdict below is bounded by those six**, and the
`spring-rabbit` search verdict is bounded to 3.1.4 alone for the reason in (c).

**How to run.** `bash scripts/probes/cp16_listener_destinations/run.sh`. It
resolves each jar through Maven (network on the first run only, cached in
`~/.m2` afterwards) and asks `javap` the four questions. Needs a JDK and Maven.
Not a test: nothing in the suite runs it, and NFR-1's no-network rule governs
the suite rather than evidence gathering.

## Expectation table

| # | Under test | Expected |
|---|---|---|
| 1 | the annotation's attributes | the destination attributes each catalog names, plus whatever else it declares |
| 2 | its meta-annotations | a `@Target`; a `@Repeatable` container or none |
| 3 | the handler annotation | no address-bearing attribute, if the catalogs are right |

## Observations

Verbatim from `run.sh`'s generated table (`probe.py` prints it; nothing here is
typed by hand). **Every column header of the first table is a version the JAR
itself reported, and not the version the coordinate list asked for** — out of
each manifest's `Implementation-Version`. `probe.py` reads the value out of the
archive it opened and ABORTS the whole run when it disagrees with the coordinate
that resolved the jar, rather than filling a mislabelled column; that is CP-5's
failure, which printed a version it believed beside output from a version it had
not run.

Row 4 is scanned over the whole post-processor rather than one method, and that
is stated because it bounds it: which method holds a rule is not a stable fact,
and row 4e/4f is this probe's own instance of that — the search is in the class
at spring-rabbit 3.1.4 and in a superclass at 4.1.1. Its cell is FILTERED to
three markers (Spring's annotation-search entry points, calls on the listener
annotation or its repeatable container, and `set*` calls into the framework's
own endpoint-config package) and DEDUPLICATED in bytecode order, because a
post-processor reads one attribute several times and the finding is the set.

## Verdict

1. **All three listener annotations are `@Repeatable`, all three frameworks
   read the container, and NOT ONE of the three catalogs names it. A method
   carrying two listener annotations therefore derives NOTHING.** Row 2, at all
   six versions: `@KafkaListener` folds into
   `org.springframework.kafka.annotation.KafkaListeners`, `@JmsListener` into
   `org.springframework.jms.annotation.JmsListeners`, `@RabbitListener` into
   `org.springframework.amqp.rabbit.annotation.RabbitListeners`. Row 4 shows
   each framework reading its container: Kafka calls `KafkaListeners.value()`
   directly; JMS calls
   `AnnotatedElementUtils.getMergedRepeatableAnnotations(element, JmsListener,
   JmsListeners)`, naming both classes; spring-rabbit 3.1.4 streams
   `RabbitListener` out of a `MergedAnnotations` view.

   javac writes the CONTAINER and not the annotation on such a method (JLS
   9.7.5), so the class file carries no `@KafkaListener` at all and
   `derive_endpoints.sql`'s `mc.fqn = a.annotation` join matches nothing. Every
   destination on that method is dropped, silently, beside its single-listener
   neighbour which derives normally. **This is the exact shape
   `spring-scheduling.yml` names a `container:` key to avoid** — the difference
   being that the `scheduled_work` style HAS such a key and `annotation_driven`
   has none. Registered as **`OI-36`**; stated in `docs/COVERAGE.md`.

2. **`spring-kafka.yml`'s destination claim is correct, and its stated
   under-report is confirmed.** Row 1: `topics()` is `String[]`,
   `topicPattern()` is `String`, `topicPartitions()` is `TopicPartition[]` — at
   3.1.4 and 4.1.1 alike, which is what the catalog's `CHECKPOINT FACT` comment
   said without naming a version. Row 4: the post-processor reads all three and
   feeds them to `setTopics`, `setTopicPattern` and `setTopicPartitions` on its
   endpoint. So `path_from: [topics, topicPattern]` names two of the framework's
   three destination sources, and the third — a nested annotation type — is the
   under-report `docs/COVERAGE.md` already states.

3. **`spring-jms.yml`'s destination claim is correct and its attribute list is
   small enough to be certain about.** Row 1: `@JmsListener` declares six
   attributes at 6.1.6 and 7.0.9, of which `destination()` is the only address
   and it is genuinely scalar — the catalog's comment, now measured. Row 4 shows
   the post-processor reading `destination`, `selector`, `subscription`,
   `concurrency`, `containerFactory` and `id`, and no seventh source of a
   destination exists to miss.

4. **`spring-rabbit.yml`'s three-way split is confirmed, including the two it
   declines to read.** Row 1: `queues()` is `String[]`, `queuesToDeclare()` is
   `Queue[]` and `bindings()` is `QueueBinding[]`. Row 4: the post-processor
   reads all three. So a listener naming its queue only through
   `@QueueBinding` or `@Queue` derives nothing here — which the catalog states
   and `docs/COVERAGE.md` records, and which is now measured rather than
   remembered.

5. **Both polymorphic handler annotations declare `isDefault(): boolean` and
   nothing else, at every version read.** Row 3. `spring-kafka.yml`'s and
   `spring-rabbit.yml`'s claim that `@KafkaHandler`/`@RabbitHandler` carries no
   address of its own — and so reaches one only through the class-level
   listener acting as a prefix — is exactly right. JMS has no such annotation
   and its catalog declares no prefix, which agrees.

6. **`@Target` is measured, and it is not the same across the three.** Row 2:
   `@KafkaListener` and `@RabbitListener` are legal on `TYPE`, `METHOD` and
   `ANNOTATION_TYPE`; `@JmsListener` on `METHOD` and `ANNOTATION_TYPE` only. So
   the class-level shape both Kafka and Rabbit catalogs model is legal in those
   two frameworks and impossible in JMS — `spring-jms.yml` declaring
   `prefix_annotation: null` is the framework's own rule rather than a
   simplification. All three are legal on `ANNOTATION_TYPE`, which is the
   composition case `derive_endpoints.handler-is-a-method` exists for.

7. **spring-rabbit 3.1.4 searches the TYPE HIERARCHY, and we match the
   declaration alone.** Row 4e: `MergedAnnotations.from(element,
   SearchStrategy.TYPE_HIERARCHY)` — the strategy arrives as a constant this
   probe can read, so it is measured rather than inferred. A `@RabbitListener`
   declared on a superclass method or an interface method therefore registers a
   listener on the implementing bean, and this repository sees an annotation
   fact only on the declaration that carries it. Registered as **`OI-37`**.

   **Its boundary.** Kafka's `findMergedAnnotation` and JMS's
   `getMergedRepeatableAnnotations` carry NO strategy constant, so what they
   search is Spring's own contract and is NOT measured here. The row is scoped
   to spring-rabbit 3.1.4 and says nothing about the other two, or about
   spring-rabbit 4.1.1, whose search moved into an artifact this probe does not
   open.
