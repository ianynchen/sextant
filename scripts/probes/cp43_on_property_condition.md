# CP-43 — what `@ConditionalOnProperty` declares and how its condition compares a value

**Version scope.** Everything below is measured against **`spring-boot-autoconfigure` as its
own manifest states it** (`Implementation-Version` — `4.1.1` when this record was made), read
by `probe.py` out of the jar in the local Maven repository — never the directory name this harness found it under, which is the
CP-5 failure the convention exists to prevent. The rule is Spring Boot's and a later release
is free to change it, so the verdicts here bound to the version in the table and to nothing
wider.

**Why it was measured.** The second condition the `conditional-controllers` cell reads (spec
`docs/superpowers/specs/2026-10-21-conditional-controllers-design.md`): a controller under
`@ConditionalOnProperty(name = "orders.legacy", havingValue = "true")` exists where the key
resolves to that value. The verdict per environment comes from `resolved_config`; the rule
for comparing — case, the empty `havingValue`, the absent key — has to be the framework's.

## What the rows say

**Row 1 — five members.** `value()` and `name()` are the key's name (aliases; the condition
reads both), `prefix()` is joined in front of each with a `.`, `havingValue()` is the expected
value, `matchIfMissing()` the verdict for an absent key. The structured expression this
analysis stores is `{key, having_value, match_if_missing}`, one per name.

**Row 2 — comparison is case-insensitive, and an EMPTY `havingValue` means "not `false`".**
`Spec.isMatch` tests `StringUtils.hasLength(havingValue)`: with a value, `equalsIgnoreCase`
against the property; without one, the property must not `equalsIgnoreCase("false")`. So
`@ConditionalOnProperty("orders.legacy")` holds for `orders.legacy=true`, `yes`, `1` and
`anything`, and fails only for `false`/`FALSE`.

**Row 3 — an absent key is decided by `matchIfMissing`, and by nothing else.** Read off the
annotation into the `Spec` and consulted when the property resolves to nothing: `true` holds,
`false` (the default) fails. This analysis applies exactly that: a key with no value in an
environment holds iff `match_if_missing`; a key whose value is a placeholder nobody filled is
`unresolved` there, because the framework would see SOME value and this analysis does not know
which.

**Row 4 — a prefix is joined with one dot, never two.** `Spec.getPrefix` trims the attribute
and appends `.` only where the text does not already end in one, so `prefix = "orders."` and
`prefix = "orders"` both name `orders.legacy`. The pass does the same (review fix, 2026-10-22:
the first version wrote `orders..legacy` for the former and found nothing).

**Row 5 — nineteen conditions, two of them evaluated.** Every annotation in the `condition`
package is built on `@Conditional` (CP-42 row 4) and names a `Condition` CLASS — code, not
configuration. `@ConditionalOnProperty` is the one this analysis evaluates (rows 1–4);
`@Profile` is CP-42's. The other eighteen, and `@Conditional` itself, are NAMED by the
catalog's `other` entry and written verbatim with `holds = unresolved` in every environment
(spec §4), so a controller under `@ConditionalOnExpression` or `@ConditionalOnBean` reads as
conditional rather than as always served. `@ConditionalOnBooleanProperty` and the two
`*Properties` forms are property-like and deliberately in that set: nothing here measured how
they compare, and a guess about a near neighbour is still a guess.

## What this does NOT measure

* **`@ConditionalOnBooleanProperty`, `@ConditionalOnExpression`, `@ConditionalOnBean`,
  `@Conditional(SomeClass.class)`.** Code deciding existence, not configuration; a row carrying
  one is reported with the annotation verbatim and `holds = unresolved`.
* **Relaxed binding** (`orders.legacy` vs `ORDERS_LEGACY` vs `orders-legacy`): the key is
  compared as spelled against `resolved_config`'s own key paths, which the config layer already
  normalises per source format.
