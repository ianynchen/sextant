# W18 — `PubSubTemplate`'s unread inbound methods (F2 §3.9)

Run: `scripts/probes/w18_pubsub_inbound/run.sh`. Everything below the rule is that
script's own output, pasted verbatim.

**Version scope (§5.4).** Read against **spring-cloud-gcp-pubsub 5.1.2**, the version
the jar's own manifest reports in the column header below, never inferred from the
path it was cached at — the run aborts when the two disagree. This is the version
`spring-pubsub.yml`'s `measured:` block already claimed for its `publish` rows, so the
inbound rows added here are bounded by the same evidence as the outbound ones rather
than by a second, looser statement. A release between this and any other is unverified,
not supported: an overload gaining a parameter changes a descriptor, and a descriptor
that no longer matches derives silence.

## What was wrong, and what "unread" cost

`spring-pubsub.yml` declared ONE inbound method. Section 1 enumerates the class's own
declared methods and finds **ten** that consume — the count §3.9 states, now generated
from the jar rather than written into a document, so a release adding an eleventh
changes this table instead of going unnoticed.

The nine unread ones did not derive a partial row or an open question. They derived
**nothing**, and nothing is the same output a module that consumes no Pub/Sub produces.
That is the failure mode GUIDELINES §8 exists for: absence that cannot be told from
absence. A pull-based consumer — an ordinary shape, and the only shape available to a
batch job — was invisible.

## Why every one of them is a boundary (GUIDELINES §8.6)

§8.6 asks for a chain of evidence reaching the point where consumption provably
happens, every link either a traced call or a measured framework rule. **The ten split
into two families with different chains, and saying "the call IS the consumption" of all
ten would be wrong about two of them.**

For the eight `pull*` methods the chain is one link: `pull`, `pullAndAck` and `pullNext`
return messages, so there is no later terminal to reach and a trace arriving at the call
is the whole chain.

`subscribe` and `subscribeAndConvert` return a `Subscriber` — which is precisely the
object that is not a boundary until something starts it. Their chain is two links, and
the second is a **measured** framework rule rather than an assumption:
`PubSubSubscriberTemplate.subscribe` starts the subscriber ITSELF before handing it
back. `javap -c` on spring-cloud-gcp-pubsub 5.1.2:

    19: invokeinterface SubscriberFactory.createSubscriber:(…)Lcom/google/cloud/pubsub/v1/Subscriber;
    26: invokevirtual   com/google/cloud/pubsub/v1/Subscriber.startAsync:()Lcom/google/api/core/ApiService;
    31: areturn

So the caller receives an already-started subscriber. **This stops being true if a
release moves the start out of the template**, and re-running this probe would not
detect that — the check it needs is `OI-65`.

Both families differ from `Subscriber.newBuilder(...).build()`, where construction
subscribes to nothing and nothing starts it. That path belongs to
`google-pubsub-subscriber.yml` and is **not** closed here — see the note below.

## What is declared, and what is deliberately NULL

Section 2 shows which of the ten capture a payload type: **three do** —
`subscribeAndConvert` at argument 2, `pullAndConvert` and `pullAndConvertAsync` at
argument 3. The other seven hand back an untyped envelope
(`AcknowledgeablePubsubMessage`, or a raw `PubsubMessage`). Those rows therefore derive
an **address with no payload shape**, which is the honest answer — the subscription is
real and the message type is not stated at the call site. Deriving a shape from the
return type would be fabrication, and the address is what makes the row a boundary.

`subscribe` was previously left out on the reasoning that "no fixture call reaches it,
and it carries no payload capture at all". Neither is a reason to omit a real boundary:
a fixture is not the estate, and a missing payload shape is a NULL column rather than a
missing row.

## What this probe does NOT close

§3.9 pairs the nine methods with a second change — replacing an unread `.startAsync()`
conjunct in `google-pubsub-subscriber.yml`. **That catalog names no such conjunct**, and
does not appear to have named one when §8.6 was written: its comment states the opposite
position outright, that "the registration is the evidence, so this style needs no
execute-terminal". The over-report §8.6 describes is nonetheless real — a `Subscriber`
constructed and never started derives a live inbound endpoint — but closing it is engine
work on `interface_implementation`, which today has no way to require a terminal at all.
Recorded rather than done here, because doing it from the design's description of a
conjunct that is not in the file is the mistake W17 was written up for.
