# CP-17 — the container and the class-level listener, for the four annotations the vocabulary pass left unmeasured

**Question.** The `annotation_driven` vocabulary pass of 2026-09-06 shipped
`mapping.annotations[].container` and then, in its own §8.3 audit table
(`.superpowers/sdd/2026-09-03-phase-2o-spring-surface/vocabulary-pass-report.md`),
named four annotations whose repeatability **nothing had measured** —
`@PulsarListener`, `@SqsListener`, `@KafkaHandler` and `@RabbitHandler`. Its
words for the first: *"it is now a MEASUREMENT gap rather than a grammar one …
one `javap` question against the jar the catalog already names closes it."* This
probe is that question, asked of all four at once, plus the two sibling
questions a container answer is worthless without.

Five shipped catalogs ride on the answers — `spring-pulsar.yml`,
`spring-sqs.yml`, `spring-sqs-legacy.yml`, `spring-kafka.yml` and
`spring-rabbit.yml` — and three of them are entries in
`tests/architecture/test_catalog_measurement_coverage.py::_NOT_MEASURED_YET`.

One reading answers the same six questions at every site:

| # | what it asks | why the catalogs need it |
|---|---|---|
| 1 | every attribute the annotation declares, with its TYPE | a `path_from` alias set is only as trustworthy as the enumeration it was chosen from; and for a handler annotation, the claim that no address lives on it IS this list |
| 2 | `@Target` and `@Repeatable` on it | `@Repeatable` is the fact four catalogs are silent about, and §8.1 rule 4 says a silence is only a CLAIM once it is measured. `@Target` bounds where a declaration may sit, which is what turns a class-level use from a composition into a real registration |
| 3 | whether a CONTAINER-shaped sibling exists, and what its `value()` returns | **asked separately from question 2 on purpose.** JLS 9.6.3 governs the container of a `@Repeatable` annotation — but nothing stops a framework shipping a plain annotation of exactly that shape for an author to write BY HAND, and a class file cannot tell the two apart. The two answers together are what say which mechanism a framework uses; one alone says nothing |
| 4 | whether a POLYMORPHIC HANDLER sibling exists, and what it declares | `spring-pulsar.yml` and `spring-sqs.yml` each state in a comment that their framework ships no such annotation and therefore no class-level shape. That comment is this cell |
| 5 | how the post-processor finds the annotation, and which attributes, containers and handlers it reads | an annotation the framework never reads is not a rule; a container the framework never reads is not a destination |
| 6 | where the rule is an ALGORITHM, the discovery method VERBATIM out of the sources jar | question 5 can say WHICH classes a post-processor touches and can never say in what combination — whether a container is read INSTEAD of the annotation or IN ADDITION TO it, whether a class-level branch exists at all. Guessing that off a disassembly is how `isCustomMethod` went unopened for a round and cost a Critical |

**What this probe does not settle, and the verdict must not be read past it.**
(a) **Nothing was deployed.** It records which attributes and siblings the
post-processor reads and which endpoint setter each feeds; it does not observe a
broker delivering a message. (b) **The SEMANTICS of Spring's annotation-search
entry points are not measured here**, CP-16's boundary unchanged: row 5 records
which method is called, and only `MergedAnnotations.from(element, STRATEGY)`
carries its strategy as a constant this probe can read. (c) **Question 6 opens
ONE method per family.** A rule that moved into a caller or a subclass between
the versions read is outside the cell, and rows 6e/6f are this probe's own
instance of a rule CHANGING inside the method it opened — which is the case it
catches, not the case it misses. (d) **`spring-cloud-aws-sqs`'s post-processor
splits across two classes** and row 5e says so in the framework's own words
rather than printing an empty cell, CP-16's mitigation for the CP-7 failure.

**Version scope (§5.4).** Read against **spring-pulsar 1.2.11 and 2.0.7,
spring-cloud-aws-sqs 3.1.1 and 4.1.1, org.springframework.cloud:spring-cloud-aws-messaging
2.2.6.RELEASE, io.awspring.cloud:spring-cloud-aws-messaging 2.4.4, spring-kafka
3.1.4 and 4.1.1, and spring-rabbit 3.1.4 and 4.1.1**. Two minors per framework
wherever a framework has two in scope, for CP-12's reason: a repeatability
answer is a version-scoped fact and one reading cannot say whether it is stable —
and rows 2e/2f are exactly why, because `@SqsListener`'s `@Target` is not the
same at both. The two LEGACY SQS artifacts are one version each because each IS
a different artifact under a different groupId; together they are the pair, and
`spring-sqs-legacy.yml`'s own comment names exactly these two. **Every verdict
below is bounded by those ten.**

**How to run.** `bash scripts/probes/cp17_containers_and_class_level/run.sh`. It
resolves each jar — and, for the two families question 6 opens, the matching
`-sources` jar at the same coordinate — through Maven (network on the first run
only, cached in `~/.m2` afterwards). Needs a JDK and Maven. Not a test: nothing
in the suite runs it, and NFR-1's no-network rule governs the suite rather than
evidence gathering.

## Observations

Verbatim from `run.sh`'s generated table (`probe.py` prints it; nothing here is
typed by hand). **Every column header of the first table is a version the JAR
itself reported, and not the version the coordinate list asked for** — out of
each manifest's `Implementation-Version`. `probe.py` reads the value out of the
archive it opened and ABORTS the whole run when it disagrees with the coordinate
that resolved the jar, rather than filling a mislabelled column; that is CP-5's
failure, which printed a version it believed beside output from a version it had
not run. Three artifacts report `4.1.1` and two report `3.1.4`, so the
`artifacts reporting this version` row is what a reader disambiguates a column
by.

**`ABSENT FROM THIS JAR` is an OBSERVATION and not an error.** CP-16 could
assume every class it named existed; this probe cannot, because half its
question is *"does this framework ship such an annotation at all?"* — and
`io.awspring.cloud.sqs.annotation.SqsHandler` exists at 4.1.1 and not at 3.1.1,
which is a finding rather than a broken run. Every OTHER `javap` failure still
aborts. The row letter of a question is stable across questions: `1a`, `2a`,
`3a` … all name the same (family, version) pair.

Row 5 is scanned over the whole post-processor rather than one method, CP-16's
bound unchanged, and is FILTERED to four markers (Spring's annotation-search
entry points, calls on the annotation, calls on its container or handler
siblings, and `set*` calls into the framework's own endpoint-config package),
DEDUPLICATED in bytecode order.

## Verdict

1. **NOT ONE of the eight annotations read here is `@Repeatable`, at any of the
   ten versions.** Row 2, everywhere: the kept meta-annotation set is a
   `@Target` and nothing else. That answers all four of the questions the
   vocabulary pass's §8.3 audit left open, and three of the four answers are
   *the catalog's silence was right*: `@KafkaHandler` (rows 2i/2j),
   `@RabbitHandler` (rows 2k/2l) and `@SqsListener` in all three of its
   spellings (rows 2e-2h) declare no container, and rows 3e-3l show that no
   container-shaped sibling exists for any of them to name. `spring-kafka.yml`
   and `spring-rabbit.yml` each say in as many words that their handler entry
   declares no `container` because repeatability was *"not measured at all"*.
   It is measured now, and the comment is a claim rather than an absence.

2. **`@PulsarListener` is the fourth, and its answer is different: the
   container exists, the framework reads it, and javac has nothing to do with
   it.** Rows 2a/2b carry no `@Repeatable`; rows 3a/3b read
   `org.springframework.pulsar.annotation.PulsarListeners` out of the same jar
   with `value(): PulsarListener[]` — the JLS 9.6.3 container SHAPE, on an
   annotation the language never folds into. Rows 6a/6b are what settle it, and
   they are the reason question 6 exists:

       PulsarListener ann = AnnotatedElementUtils.findMergedAnnotation(method, PulsarListener.class);
       if (ann != null) { listeners.add(ann); }
       PulsarListeners anns = AnnotationUtils.findAnnotation(method, PulsarListeners.class);
       if (anns != null) { listeners.addAll(Arrays.stream(anns.value()).toList()); }

   The framework registers the UNION — a direct `@PulsarListener` and every
   member of a hand-written `@PulsarListeners`, byte-identical at 1.2.11 and
   2.0.7. A method carrying `@PulsarListeners({@PulsarListener(topics = "a"),
   @PulsarListener(topics = "b")})` serves two topics and derived NOTHING here,
   beside a single-listener neighbour deriving normally: `OI-36`'s exact silent
   drop, reached by a different mechanism. **The `container:` key says it
   exactly** — the class file the engine reads is the same shape either way, and
   `folded_rows` never asked whose it was. Registered as **`OI-38`**.

3. **`@PulsarReader` is a whole second inbound Pulsar surface, and
   `spring-pulsar.yml` names it nowhere.** Rows 1c/1d: it declares
   `topics(): java.lang.String[]`, `schemaType()`, `startMessageId()` and five
   more. Rows 5c/5d: its own post-processor reads `PulsarReader.topics()` and
   feeds `MethodPulsarReaderEndpoint.setTopics([Ljava/lang/String;)`, then
   registers the endpoint with `PulsarReaderEndpointRegistrar`. Rows 6c/6d show
   the discovery is method-level and single —
   `findMergedAnnotation(method, PulsarReader.class)`, no container — and rows
   3c/3d confirm no `PulsarReaders` exists to look for. So every
   `@PulsarReader`-annotated consumer in a scanned module was absent from the
   export entirely. Registered as **`OI-39`**.

4. **`@SqsListener` gained a class-level, polymorphic form at 4.1.1 and
   `spring-sqs.yml` states that it has none.** Three rows in agreement:
   row 2e/2f — `@Target(METHOD)` at 3.1.1, `@Target({METHOD, TYPE})` at 4.1.1;
   row 4e/4f — `io.awspring.cloud.sqs.annotation.SqsHandler` is `ABSENT FROM
   THIS JAR` at 3.1.1 and declares `isDefault(): boolean` at 4.1.1, the
   `@KafkaHandler`/`@RabbitHandler` shape exactly; row 5f — the 4.1.1
   post-processor references `class io/awspring/cloud/sqs/annotation/SqsHandler`
   and calls `SqsHandler.isDefault()`, and the 3.1.1 one (row 5e) names it
   nowhere. Row 6f is the branch itself:

       A classListener = AnnotatedElementUtils.findMergedAnnotation(targetClass, getAnnotationClass());
       …
       if (hasClassLevelListeners) { Set<Method> handlerMethods = getHandlerMethods(targetClass);
         createAndConfigureMultiMethodEndpoint(bean, targetClass, classListener, …); }

   — against row 6e, the same method at 3.1.1, which has no `classListener` at
   all and registers method-level endpoints only. The class-level endpoint takes
   its queue names from the CLASS-level annotation's `value()`
   (`MultiMethodSqsEndpoint.builder()…queueNames(resolveEndpointNames(sqsListenerAnnotation.value()))`),
   which is `spring-kafka.yml`'s prefix shape one framework over. So
   `spring-sqs.yml`'s `prefix_from: []` / `prefix_annotation: null` and its
   comment *"No class-level listener shape for SQS"* are correct at 3.1.1 and
   **false at 4.1.1**, and every `@SqsHandler` method in a module on 4.x was
   absent from the export. Registered as **`OI-40`**.

   The `sqs-handler` family (rows 1m-6n) was **added after the first run**, for
   the reason the close itself surfaced: the `sqs` family asks `@Repeatable` of
   `@SqsListener` and reads `@SqsHandler`'s ATTRIBUTES only, so a catalog entry
   for `@SqsHandler` would have declined a container on no evidence — §8.1
   rule 4's own case. Rows 2n and 3n answer it: `@Target(METHOD)`, no
   `@Repeatable`, and no `io.awspring.cloud.sqs.annotation.SqsHandlers` in the
   jar. Appending the family left every earlier row letter naming the same cell,
   which is checked rather than assumed — the two runs' `1a`-`6l` are identical.

5. **Both legacy `@SqsListener` spellings are exactly what `spring-sqs-legacy.yml`
   says they are, and that is now measured rather than remembered.** Rows 1g/1h:
   each declares exactly `value(): java.lang.String[]` and a `deletionPolicy()`
   of its own generation's enum type — nothing else. Rows 2g/2h: `@Target(METHOD)`
   on both, so the class-level shape is not merely unmodelled but illegal, and
   the file's `prefix_from: []` is the language's rule rather than a
   simplification. Rows 3g/3h: no container-shaped sibling in either jar. Rows
   5g/5h: `QueueMessageHandler` finds the annotation with
   `AnnotationUtils.findAnnotation` and reads `value()` and `deletionPolicy()`
   and no third attribute. The catalog's `CHECKPOINT FACT` comment named both
   versions and had no evidence behind it; it does now, and it was right.

6. **`@SqsListener`'s destination claim is confirmed at a SECOND version, and
   the `@AliasFor` reading is confirmed by omission.** Rows 1e/1f: `value()` and
   `queueNames()` are both `String[]` at 3.1.1 and 4.1.1. Rows 5e/5f: the
   post-processor reads `value()` and never `queueNames()` at either version —
   which is not a contradiction of `spring-sqs.yml`'s two-alias `path_from` but
   its confirmation, because the merge happens inside
   `AnnotatedElementUtils.findMergedAnnotation` (rows 6e/6f) and `value` is the
   spelling that survives it. CP-12 Q10 measured the `@AliasFor` at 3.1.1; this
   is the read that shows what the framework does with it, at both.

7. **All three polymorphic handler annotations declare `isDefault(): boolean`
   and nothing else, and none of the three is repeatable.** Rows 1i-1l and 1n
   for the declaration — `@KafkaHandler` and `@RabbitHandler` at both versions
   of each, which is CP-16 rows 3a-3f re-read at the same two minors, plus
   `@SqsHandler` at 4.1.1. Rows 2i-2l and 2n for the meta-annotations:
   `@Target({METHOD, ANNOTATION_TYPE})` on the two Spring ones,
   `@Target(METHOD)` on the AWS one, and no `@Repeatable` anywhere. Rows 3i-3l
   and 3n found no `KafkaHandlers`, `RabbitHandlers` or `SqsHandlers` to name.
   So all three catalogs' claim that the handler carries no address of its own
   AND no container is a measured claim, where two of the three were an
   explicitly unmeasured silence before this run.

## What a reader must NOT take from this table

- **That a container-shaped sibling implies a repeated form is derived.** Rows
  3a/3b found `@PulsarListeners`; whether a catalog reads it is a catalog fact,
  and the verdicts above name the register rows that track it.
- **That `ABSENT FROM THIS JAR` means the framework has no such concept.** It
  means this probe looked for that FQN in that archive and did not find it.
  `@SqsHandler` at 3.1.1 is absent because the class did not exist yet; a
  handler annotation living in a different artifact would read the same way and
  would not be the same finding.
- **That row 5's set is every attribute a framework reads.** It is every read
  in the post-processor class this probe opened. Row 5e is the standing
  reminder: at 3.1.1 the search lives in a superclass and the cell says so.
