# CP-46 — which interfaces Spring Data registers as beans, and whether their conditions count

**Version scope.** Everything below is measured against **`spring-data-commons` as its own
manifest states it** (`Implementation-Version` — `4.1.1` when this record was made) and
**`spring-context` and `spring-core` as their own manifests state them** (`7.0.9`), read by
`probe.py` out of the jars in the local Maven repository — never the directory name this
harness found them under, which is the CP-5 failure the convention exists to prevent. The
rules are platform behaviour of Spring Data (`4.1.1`) and the Spring Framework (`7.0.9`) and
a later release is free to change any of them, so the verdicts here bound to the versions in
the table and to nothing wider.

**Why it was measured.** On spring-petclinic-rest every repository call reads "none of them"
in every environment: the module's Spring Data repositories are INTERFACES
(`@Profile("spring-data-jpa") interface SpringDataOwnerRepository extends OwnerRepository,
Repository<Owner, Integer>`), implemented at run time by a proxy the framework generates, so
no class of the module is their bean and the conditions pass saw no registration route for
them (conditional-beans Task 7b fix, ruled 2026-10-22). Which interfaces the repository
scanner registers, which it refuses, and whether an interface's own `@Profile` is evaluated
are the framework's, so they are read off the jars before the bean model
(`src/sextant/catalogs/bean-models/spring.yml`, `interface_registrations`) names them.
`src/sextant/catalogs/spring-data-rest.yml` (`repositories`, `no_repository_bean`) and CP-2
(`scripts/probes/cp2_data_rest.md`) read the same roots for the routes Data REST exposes; this
probe reads them for the bean the container registers.

## What the rows say

**Rows 1 and 6 — the repository scanner is Spring's component scanner, with its condition
check.** `RepositoryComponentProvider` extends `ClassPathScanningCandidateComponentProvider`
and does not override `isCandidateComponent(MetadataReader)`, which runs the exclude and
include filters and then `isConditionMatch` (CP-44 row 4) — so a repository interface's own
`@Profile` and other conditions are evaluated exactly as a scanned class's are.

**Rows 2 and 4 — an interface is a repository when it is assignable to `Repository` or
carries `@RepositoryDefinition`.** `InterfaceTypeFilter(Repository)` matches an INTERFACE
assignable to `org.springframework.data.repository.Repository`; `@RepositoryDefinition` is
matched on the type, its meta-annotations and its interfaces (`true, true`).

**Rows 2 and 3 — `@NoRepositoryBean` refuses the interface that carries it, and only that
one.** The exclude filter is a one-argument `AnnotationTypeFilter`, which considers
meta-annotations and NOT interfaces: a `@NoRepositoryBean` base interface is no bean, and an
interface extending it is one.

**Row 5 — two more refusals.** `Repository` itself is no bean (`isGenericRepositoryInterface`),
and a NESTED interface is kept only where `considerNestedRepositoryInterfaces` is set.

## What this does NOT measure

* **Whether repository scanning runs at all, and from which packages.** `@EnableJpaRepositories`
  or Spring Boot's auto-configuration turns it on and names the base packages; an interface
  outside them is no bean. This analysis treats every module interface the rows above admit as
  scanned — a documented claim, the same one CP-44 makes for component scanning.
* **Nested interfaces.** `considerNestedRepositoryInterfaces` is configuration
  (`@EnableJpaRepositories(considerNestedRepositories = …)`); this analysis does not refuse a
  nested repository interface.
* **Fragment implementations** (`…Impl` classes a repository interface's fragments resolve to)
  and custom `includeFilters` / `excludeFilters` handed to the scanner.
