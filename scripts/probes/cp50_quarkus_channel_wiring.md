# CP-50 — which channels Quarkus attaches a connector to, and when

**Version scope.** Everything below is measured against `quarkus-messaging-deployment` and
`quarkus-messaging` **as their own manifests state them** (`Implementation-Version` — `3.17.5`,
the fixture's Quarkus, and `3.40.1.1`, the `examples/quarkus-quickstarts` field corpus's, when
this record was made), and `quarkus-core` `3.17.5` for one annotation default, read by
`probe.py` out of the local Maven repository — never the directory name this harness found
them under, which is the CP-5 failure the convention exists to prevent. These are platform
behaviour of those releases and a later one is free to change any of them, so the verdicts
here bound to the versions in the table and to nothing wider.

**Why it was measured.** Ruling 2 of the Quarkus messaging design (spec 2026-10-24, §1) mirrors
Quarkus's wiring rule: a channel is a boundary when its connector is configured
(`mp.messaging.<dir>.<channel>.connector`), or when it is an ORPHAN and exactly one connector
of that direction is on the module's classpath; an in-memory channel gives no row. Of the 15
quickstart modules measured, 13 configure no connector key at all and rely on that attachment
(§2). Which channels are orphans, what makes a channel connector-managed, when the one
connector is attached, the flag that gates it and its default are the framework's, so they are
read off the jars before the catalog's wiring rule states them.

## What the rows say

**Rows 1 and 11 — an orphan is a name only one direction uses, and no connector manages.**
`detectOrphanChannels` keys each direction's channels by name, removes the other direction's
names from each, and of what remains produces an orphan for every name whose channel is not
connector-managed. So a channel both produced and consumed in the module (an in-memory pair)
is never an orphan, and a channel with a configured connector is never one either.

**Rows 2–4 and 12–14 — a channel is connector-managed when its connector key is set and it is
enabled.** The connector comes from `<dir>.<channel>.connector` under the messaging prefix
(`mp.messaging.` at 3.17.5, `quarkus.messaging.` at 3.40.1.1 — rows 9 and 19 say why both are read), and a
channel whose `…enabled` is false (default `true`) produces no channel at all. A channel name
containing `.` is written into the key quoted (rows 5, 15).

**Rows 6 and 16 — a connector on the classpath is a bean carrying `@Connector`,** incoming when
it implements `IncomingConnectorFactory` or `InboundConnector`, outgoing when it implements
`OutgoingConnectorFactory` or `OutboundConnector`, named by the qualifier's value. Every
SmallRye connector CP-51 reads implements both of the SmallRye pair.

**Rows 7 and 17 — the attachment.** For each direction separately: when the set of that
direction's connector names has exactly one member, and the build-time flag is on, every orphan
of that direction gets that connector. With two connectors of a direction, or none, nothing is
attached and the orphan stays unwired. The attachment is written as a `RunTimeConfigurationDefaultBuildItem` of
`mp.messaging.<dir>.<channel>.connector` — a run-time configuration DEFAULT, not a fixed value.

**Rows 8 and 18 — a configured connector wins, and an unknown one fails the build.** Every
connector-managed channel is matched against the connector beans by direction and name
(case-insensitive); a match makes it a `ConnectorManagedChannelBuildItem`, no match is a
`WiringException`, "configured with an unknown connector".

**Rows 9 and 19 — the key's spellings.** 3.17.5 registers no configuration interceptor: only
`mp.messaging.…` is read. 3.40.1.1 registers `ReactiveMessagingConfigBuilderCustomizer`, which
installs a fallback from `quarkus.messaging.{incoming,outgoing}.…` to `mp.messaging.…` and a
relocation from `mp.messaging.…` to `quarkus.messaging.…`, so at 3.40.1.1 either spelling of
a channel's attribute names the same value.

**Rows 10 and 20 — the flag.** `quarkus.messaging.auto-connector-attachment`, build time,
default `true`, at both versions (3.17.5 spells it `@ConfigRoot(name="messaging")` with
`quarkus-core`'s `prefix()` default `quarkus`; 3.40.1.1 `@ConfigMapping(prefix="quarkus.messaging")`).

## What this does NOT measure

* **The interceptors' precedence.** Rows 9 and 19 read which key each interceptor rewrites to
  which; what a `RelocateConfigSourceInterceptor` and a `FallbackConfigSourceInterceptor` do
  with the rewritten name — the relocated name read in place of the original, the fallback read
  when the original is absent — is `smallrye-config`'s, documented and not read here. Which
  spelling wins when a module sets BOTH to different values is therefore not measured.
* **That a run-time setting overrides the attachment.** A `RunTimeConfigurationDefaultBuildItem`
  is, by its name and Quarkus's documentation, a default any run-time configuration source
  replaces; the bytecode read here shows the item type written, not how the configuration
  system ranks it.
* **What happens to an orphan nothing attaches to.** With zero or two connectors of a
  direction no default is written; the application's behaviour then (a run-time wiring failure,
  or a channel that never receives) is SmallRye's runtime graph, not read here. Ruling 2's
  answer — `unresolved`, naming the candidates — is the design's, not the framework's.
* **Plain SmallRye on another container.** The orphan rule is Quarkus's build step; SmallRye
  on its own does not attach a connector to an unconfigured channel, and this probe does not
  read its runtime.
