# W17 — does a WebFlux `@Controller` derive? (F2 §3.7, G-38)

Run: `scripts/probes/w17_webflux_controller/run.sh`. Everything below is that
script's own output, pasted verbatim.

**Version scope (§5.4).** Read against **spring-webmvc 6.1.6 and 7.0.2** and
**spring-webflux 6.1.6 and 7.0.2** — each version self-reported by the jar's own
manifest in section 1's table, never inferred from the path it was cached at. The
two versions are the ends of the range `spring-mvc.yml` already claimed for
`spring-webmvc`; a release between them is unverified, not supported. Section 3
compiles and runs against **spring-context 6.1.6, spring-core 6.1.6, spring-web
6.1.6 and reactor-core 3.6.5**. Widening any of these means adding the coordinate
to `scripts/probes/w17_webflux_controller/run.sh` and re-running, never assuming:
a later release could narrow either `isHandler` and the whole verdict turns on the
two being the same.

## What was asked, and why the answer is a correction rather than a build

G-38 states a mechanism and a consequence:

> `spring-mvc.yml` carries the `@Controller` gate behind
> `detect.coordinates: [org.springframework:spring-webmvc]`, which a WebFlux module
> does not have (…) So `@Controller` + `@ResponseBody`, or `@Controller` returning
> `Mono<String>`, matches neither catalog and its whole HTTP surface is absent.

The design turned it into a build item — *"This is a bug and it gets fixed"* — and
said which fix to pick is **"decided by measurement of the two gates"**. So the
measurement came first, and it did not find the bug.

**All four shapes derive, in a build that declares `spring-webflux` and not
`spring-webmvc`, and they derive identically to the same build declaring
`spring-webmvc`.** Section 3 is the run. The reason is section 2: **this catalog's**
`detect.coordinates` is read by nothing. Two styles read that key
(`derived_resource`, `config_join`), plus any catalog that sets `detect.required`
— and `spring-mvc.yml` is none of those. *Not "no `annotation_driven` catalog's
coordinates are read": `spring-stomp` and `spring-rsocket` are `annotation_driven`
and set `detect.required`, so theirs are read and do decide what derives. The
over-general form would tell the next author that adding `detect.required` to an
`annotation_driven` catalog does nothing, which is backwards.* For this catalog
the key was inert, so the gate G-38 describes has never existed.

**How the prediction went wrong, stated plainly, because it is the reusable part.**
G-38 was written by reading `spring-mvc.yml`, seeing a `detect.coordinates` line,
and reasoning about what a gate keyed on that coordinate would do. Nobody asked
whether a consumer reads it. That is GUIDELINES §8.1 — measure, never predict — and
it is the same shape as §2's "a capability with no consumer is half-shipped", seen
from the other side: a *declared gate* with no consumer misled a reader into
predicting an outcome the code does not produce. `ingress/catalogs/yaml_source.py`
says so in as many words about the shape check for this very key — "citing it as
the consumer of `detect.coordinates` would satisfy GUIDELINES §5.3 falsely" — and
the gap analysis cited the catalog file itself instead.

## What did change, and why it is not nothing

The sentence `spring-mvc.yml` made was **false**, whether or not anything read it:
`@Controller` is served by both web stacks, and the list named one. Section 1
measures that directly — each artifact ships a `RequestMappingHandlerMapping`, and
the `isHandler` predicate that decides which beans it scans is byte-for-byte
identical in the two, at both versions measured.

Leaving a false sentence in place because nothing currently reads it would have
been safe only until someone read it. W16 shipped `detect.required`, which is a
catalog author's opt-in to having their coordinate list honoured. One line in this
file would have turned G-38's prediction into G-38's bug for the first time, and
the author adding it would have had every reason to trust the list already there.
So the list now names both coordinates, cites the measurement, and the
`displayName` no longer says "server-rendered controllers" — which section 3 shows
is not what this catalog derives.

The plan's acceptance for W17 is *"a WebFlux `@Controller` derives its endpoints"*.
It does, and `tests/application/test_endpoints.py` now pins it against a build that
declares the WebFlux coordinate alone.
