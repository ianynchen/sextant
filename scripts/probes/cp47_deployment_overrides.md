# CP-47 — what a deployment can set that the configuration files a module ships cannot decide

**Version scope.** Everything below is measured against **`spring-core` as its own manifest
states it** (`Implementation-Version` — `7.0.9` when this record was made), **`spring-boot`
as its own manifest states it** (`4.1.1`) and **`spring-boot-autoconfigure` as its own
manifest states it** (`4.1.1`), read by `probe.py` out of the jars in the local Maven
repository — never the directory name this harness found them under, which is the CP-5
failure the convention exists to prevent. The rules are platform behaviour of the Spring
Framework and Spring Boot and a later release is free to change any of them, so the verdicts
here bound to the versions in the table and to nothing wider.

**Why it was measured.** The conditional-beans pass (spec 2026-10-22) decided a bean's
`@Profile` and `@ConditionalOnProperty` from the files the module ships: an environment's
profile file, its base file, the profiles that base file activates. On three field modules
that produced 240 decided property verdicts on `apollo-portal`, 117 profile and property
verdicts on `spring-petclinic-rest`, and a handful on `jhipster-sample-app` — every one of
them a statement about what the repository's FILES say, written in the document as what the
bean does. A deployment is free to say otherwise (an OS environment variable, a command-line
argument, a ConfigMap or a Helm value rendered into either), so the question is whether
Spring Boot lets it. Spec 2026-10-23 deployment-set-conditions §3a turns the answer into
catalog data (`set_by: deployment` on the `profile` and `property` condition kinds of
`src/sextant/catalogs/bean-models/spring.yml`); this is the probe that data cites.

## What the rows say

**Row 1 — the command line is first.** `configurePropertySources` puts the command-line
source at the front of the property sources (`addFirst`), or, when a `commandLineArgs` source
already exists, replaces it with a composite that has the application's arguments first.
Nothing is added ahead of it by this method; the only `addLast` is the application-info source.

**Row 2 — the OS environment precedes every config-data file.** `StandardEnvironment` adds
`systemProperties` and then `systemEnvironment` to the environment, each at the end; Boot's
`ConfigDataEnvironment` then adds every config-data source (`application.properties`,
`application-<profile>.properties`, the YAML forms, `spring.config.import`) at the end of
what is already there. So `application.properties` and a profile file are LAST in the
order, behind both the command line and the OS environment. `spring.application.json`,
the JNDI and servlet sources, are not measured.

**Row 3 — an environment variable names a property by upper-casing it.** The framework
resolves `spring.profiles.active` against the OS environment as `SPRING_PROFILES_ACTIVE`
(`.` and `-` become `_`, then upper case), and the binder reads `BILLING_ENABLED` as the
property `billing.enabled`. So a deployment that sets `BILLING_ENABLED=true` sets
`billing.enabled`, with no file and no flag naming it.

**Row 4 — the first source holding a key is the answer; nothing is merged.** The resolver
walks the sources in order and returns the first non-null value it meets, converted. So a
key present in a higher source is not read from a lower one, and a file cannot reach past
the deployment that set the same key above it. With rows 1-3: `SPRING_PROFILES_ACTIVE=jdbc`
in the OS environment, or `--spring.profiles.active=jdbc` on the command line, is the value
the active-profile read (CP-45 row 4: `getProperty` first) returns, whatever
`application.properties` says; `BILLING_ENABLED` is likewise the value `billing.enabled`
reads.

**Row 5 — `@ConditionalOnProperty` reads through that same resolver.** `OnPropertyCondition`
asks the context's `Environment` — a `PropertyResolver` — `containsProperty` and
`getProperty`, so it sees exactly the order rows 1-4 measure. (`@Profile` reads the active
profiles the container was handed, which Boot derives through the same `getProperty`:
CP-45 row 4, and CP-42.)

**What the catalog does with it.** `profile` and `property` carry `set_by: deployment`
(`set_by_probe:` this record) beside their evaluation rule (`by:` CP-42, CP-43): the pass
decides them only by the environment's own definition — a profile environment `p` holds
`p` — and otherwise reports them not evaluated, because a repository file is the lowest
source and any deployment may outrank it. `presence` and `other` do not carry it: a bean's
presence is decided by what the code registers, and `other` is already never evaluated.

## What this does NOT measure

* **That a given deployment sets anything.** The probe shows a deployment CAN override a
  file; it cannot show one does. The verdict "not evaluated" is therefore an honest
  statement of what the repository alone decides, not a claim the file's value is wrong.
* **The binder's own walk.** Row 4 reads `PropertySourcesPropertyResolver` (what `getProperty`
  and `OnPropertyCondition` use). `Binder.findProperty`, used for the list and `Set` forms
  (`spring.profiles.active[0]`), is a separate walk over the same sources and is not read
  here.
* **Other sources.** `spring.application.json`, JNDI, the servlet context and config-tree
  (`spring.config.import=configtree:`) sources, and test property sources, sit at other
  places in the order and are not measured; none of them is a repository file.
* **Profile-specific files.** A profile-specific file cannot set `spring.profiles.active`
  (CP-45 row 7), so the deployment, not the repository, selects which profile files are read
  at all.
