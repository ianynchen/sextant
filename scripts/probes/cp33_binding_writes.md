# CP-33 — what the bytecode shows for a binding assigned OUTSIDE an initialiser

Capability 9.19 (spec §4, §5a), plan Task 11 Step 1. **Probe first**, because this is the
only edge of the value walk with no fact behind it, and a wrong binding-write fact
fabricates silently everywhere a binding is read.

Re-run it rather than trusting this file: `JAVA_HOME=<jdk21+> bash
scripts/probes/cp33_binding_writes/run.sh`. The `javap` output *is* the measurement.

**Version scope.** Everything below is measured at **21.0.12.1** — the version
`javac -version` itself reported, not the toolchain named by `JAVA_HOME` — with
`jakarta.annotation:jakarta.annotation-api:2.1.1` on the compile classpath for
`@PostConstruct` alone. A bytecode shape is compiler-scoped: a later `javac` is free to emit
a different sequence for the same source, and the verdicts here bound to the version that
produced the table.

## What the existing fact does, for comparison

`MethodFlow.fieldWrites` emits `field_write` for `<init>` only, and matches one exact
triple — `ALOAD 0; xLOAD k; PUTFIELD`, with the label/line/frame pseudo-instructions
filtered out so they do not count as "something intervened". The loaded slot is mapped to a
declared parameter index, and the fact is `{field, from_parameter}`. A computed assignment
never presents the triple, so it emits nothing.

So the question this probe asks is narrow and exact: **outside `<init>`, which shapes
present that triple, and which do not?**

## Expectation table

| # | shape | expectation | observed |
|---|---|---|---|
| 1 | a setter assigning its parameter | the triple, unchanged | **confirmed** — `aload_0; aload_1; putfield` |
| 2 | `@PostConstruct` assigning a literal | ? | **the value load is `ldc`, not an `xLOAD`** — no triple |
| 3 | a computed assignment (`a + b`) | no triple | **confirmed** — `invokedynamic` intervenes |
| 4 | a method that writes then reads the field | ? | **the triple stands**; the `getfield` is separate instructions after it |
| 5 | a second parameter after a `long` | slot mapping holds | **confirmed** — `aload_3`, and `parameterSlotsOf` computes `[1, 3]` |
| 6 | a static initialiser | ? | **`ldc; putstatic`** — no receiver load, and `PUTSTATIC` not `PUTFIELD` |
| 7 | a field assigned a CALL's result | ? | **an `invokeinterface` and a `checkcast` intervene** — no triple |

## Observations

Generated by `scripts/probes/cp33_binding_writes/run.sh`. The column header is the
version `javac -version` reported, not the parameter passed in as `JAVA_HOME`;
`@PostConstruct` came from jakarta.annotation-api 2.1.1.

| shape | 21.0.12.1 |
|---|---|
| a setter assigning its parameter | `aload_0; aload_1; putfield; return` |
| `@PostConstruct` assigning a literal | `aload_0; ldc; putfield; return` |
| a computed assignment | `aload_0; aload_1; aload_2; invokedynamic; putfield; return` |
| write then read the same field | `aload_0; aload_1; putfield; getstatic; aload_0; getfield; invokevirtual; return` |
| a second parameter after a `long` | `aload_0; aload_3; putfield; return` |
| a static initialiser | `ldc; putstatic; return` |
| a field assigned a CALL's result | `aload_0; aload_1; iconst_0; invokeinterface; checkcast; putfield; return` |

**1. A setter is the triple verbatim.** `aload_0; aload_1; putfield` — identical in shape to
what a constructor presents. For this case capability 9.19 is *literally* lifting the
`!"<init>".equals(method.name)` guard; no new matching logic.

**2. `@PostConstruct` does not write a parameter. It writes a CONSTANT, and the fact
grammar cannot carry that.** The middle instruction is `ldc`. `isLoad()` admits
`ILOAD`..`ALOAD` and `LDC` is neither, so no triple presents and `indexOfSlot` would have
nothing to map. **This is the finding that changes Task 11's scope**: `field_write`'s shape
is `{field, from_parameter}`, and a constant assignment has no parameter to name. The
annotation is immaterial — it is a class-file attribute and changes no instruction, which
the row above shows by carrying the same shape any non-constructor literal assignment would.

**3. A computed assignment is refused for free.** Two loads and then an `invokedynamic`
before the `putfield`: the triple never presents, so the existing "direct traces only"
discipline holds outside `<init>` with no extra work. This is the case that would fabricate
if the matcher were loosened to "a `putfield` somewhere after a load", and it is why the
triple is the rule rather than a dataflow pass.

**4. A write followed by a read of the same field keeps its triple.** The write is the first
three instructions and the read is `aload_0; getfield` later; they do not interleave, so the
triple is unambiguous. Worth stating because the plan asked for this case by name: the read
does not invalidate the write fact and nothing here needs ordering logic.

**5. The slot mapping is unchanged outside `<init>`, and the wide-parameter row proves it.**
`this` is slot 0, the `long` occupies 1–2, so the `String` is slot 3 — and
`parameterSlotsOf(desc, 1)` already computes `[1, 3]` for `(long, String)`, mapping slot 3
to parameter index 1 with no change. **An instance method has `this` at slot 0 exactly as a
constructor does**, which is why `firstSlot: 1` stays right.

**A STATIC method is the exception and must not be overlooked**: its parameters start at
slot 0, and `parameterSlotsOf` already takes `firstSlot` for that reason — its own comment
says "0 for a static method, which is the only difference between the two callers". So
lifting the guard requires passing the right `firstSlot` per method, not the constant 1.

**6. A static initialiser is out of reach for two independent reasons.** There is no
receiver load — a static field has no `this` — and the opcode is `putstatic`, not
`putfield`, so both halves of the triple's anchor are absent. And as with `@PostConstruct`
the value is a constant, so even a `putstatic` variant would have no parameter to name. A
`static final` constant is already covered by a different mechanism entirely: javac INLINES
a compile-time constant at every use site, so it reaches a call site as a literal and never
as a field read (`shapes/identity_calls.py` records that).

**7. A field assigned another CALL'S RESULT presents no triple — and this is the row that
decides `akka-pekko-actors`.** The sequence is `aload_0; aload_1; iconst_0;
invokeinterface; checkcast; putfield`: the receiver load is there and the `putfield` is
there, but what sits between them is a CALL, not an `xLOAD`, so `isLoad()` refuses it for
the same reason it refuses `@PostConstruct`'s `ldc`. **`ActorRef ref = system.actorOf(props,
"worker")` is exactly this shape**, which means a parameter-sourced capability 9.19 would
not reach an actor reference at all. Measured here rather than inferred from the matcher,
because the inference was the thing that needed checking: spec §4 states the sixth edge
"is what closes `akka-pekko-actors`", and on the characteristic actor shape that is false.
A setter-injected `ActorRef` (row 1) would be reached; one obtained from the factory the
framework's own documentation uses would not.

## What this means for capability 9.19

**Lifting the `<init>` guard covers exactly one of the three shapes the plan named.** A
setter — and any non-constructor method assigning a bare parameter — presents the triple
and needs no new matching logic beyond a per-method `firstSlot`. `@PostConstruct` and the
static initialiser both assign CONSTANTS, which `{field, from_parameter}` cannot express,
so they are not reached by widening the method filter and would need a different fact.

That is a scoping question rather than an obstacle, and it belongs to whoever rules on
9.19's shape: **a parameter-sourced capability is small and safe; a value-sourced one is a
new fact.** This probe does not decide it, and the plan's Step 2 ("emit the fact only where
the assignment is directly traceable") is satisfied either way, since a constant assignment
is as directly traceable as a parameter one — the question is only what the fact can say.

**And row 7 withdraws one of the spec's claims for the capability.** §4 says the sixth edge
"is what closes `akka-pekko-actors`" and that COVERAGE's *"possibly permanent"* tier "is a
statement about this missing capability rather than about actors". The first half does not
hold: an `ActorRef` from `actorOf` is a call result, which no `{field, from_parameter}` fact
can carry, so 9.19 at the scope this probe measured would leave that framework exactly where
it is. The second half still stands, and is now sharper — the tier is a statement about a
value-sourced binding write, which is a bigger fact than the one Task 11 was scoped to
build.
