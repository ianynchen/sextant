# CP-42 — what `@Profile` declares, how its condition decides, and what a profile expression admits

**Version scope.** Everything below is measured against **`spring-context` and `spring-core`
as their own manifests state them** (`Implementation-Version` — `7.0.9` for both when this
record was made), read by `probe.py` out of the jars in the local Maven repository — never the directory name this harness found them under,
which is the CP-5 failure the convention exists to prevent. Both are platform behaviour of
the Spring Framework and a later release is free to change either, so the verdicts here bound
to the versions in the table and to nothing wider.

**Why it was measured.** COVERAGE's `conditional-controllers` cell (spec
`docs/superpowers/specs/2026-10-21-conditional-controllers-design.md`, ruled 2026-10-22): a
controller under `@Profile(…)` exists in some environments and not others, and the row must
STATE that, structured, with a per-environment verdict. The verdict is only honest if the
framework's own rule is the one applied — which members the annotation has, whether several
listed profiles are any-of or all-of, and what a profile STRING may contain beyond a name.

## What the rows say

**Row 1 — one member, `String[] value()`.** A `@Profile` carries a list of expressions and
nothing else; there is no `prefix`, no `matchIfMissing`, nothing to read beside the list.

**Row 2 — ANY expression matching accepts.** `ProfileCondition.matches` hands the whole
`value` array to `Environment.matchesProfiles(String[])`, which accepts if any one expression
matches the active profiles. So `@Profile({"kubernetes", "nacos-discovery"})` holds in an
environment named either; the structured expression this analysis stores is the list, read
as any-of.

**Row 3 — a profile string is an EXPRESSION, not a name.** The parser tokenises on `()&|!`:
`!prod` negates, `a & b`, `a | b` and parentheses compose. This analysis evaluates exactly two
shapes — a bare name (holds where that profile is active) and `!name` (holds where it
is not) — and reports any expression carrying `&`, `|` or a parenthesis as `unresolved` in
every environment. Stated, not evaluated: an environment's active profiles are the profile its
file names plus what the base configuration's `spring.profiles.active` and `.include` list
(CP-45, which reads them), so a bare name and its negation are decided against that set, and a
boolean composition over several active profiles is a claim this analysis does not make.

**Row 4 — the generic condition is a class.** `@Conditional` takes `Condition` classes, each
of which is code that runs against a context this analysis never sees, so no verdict is
possible and none is given: the catalog's `other` entry names it (with CP-43 row 5's
eighteen) and the row is written verbatim, `unresolved` everywhere.

## What this does NOT measure

* **Which profiles are active at runtime.** The environments this analysis evaluates against
  are the profile FILES the module ships, which is what `resolved_config` already resolves.
  When this record was made an environment's active profile was taken to be its file's name
  alone; that was superseded on 2026-10-22 by CP-45, which reads `spring.profiles.active`,
  `.include` and `.default` from configuration. A value that is a placeholder nothing fills
  (`${apollo_profile}`) leaves every profile it could name `unresolved`.
* **`@Profile` on a `@Bean` method** (`OI-108`, closed by `conditional-beans`): the same
  annotation, the same rule, read from the bean's own table — not measured here.
