# CP-45 — which keys name an environment's active profiles, and which profile is active when none is named

**Version scope.** Everything below is measured against **`spring-core` as its own manifest
states it** (`Implementation-Version` — `7.0.9` when this record was made) and
**`spring-boot` as its own manifest states it** (`4.1.1`), read by `probe.py` out of the
jars in the local Maven repository — never the directory name this harness found them under,
which is the CP-5 failure the convention exists to prevent. The rules are platform behaviour
of the Spring Framework (`7.0.9`) and Spring Boot (`4.1.1`) and a later release is free to
change any of them, so the verdicts here bound to the versions in the table and to nothing
wider.

**Why it was measured.** A `@Profile` condition (CP-42) holds where its profile is ACTIVE.
PR #61 took an environment's active profile to be its config FILE's name only, so on
spring-petclinic-rest — whose `application.properties` sets
`spring.profiles.active=h2,spring-data-jpa` — every Spring Data JPA repository read as
existing in no environment, and on Apollo — `spring.profiles.active: ${apollo_profile}` —
the `ldap` / `oidc` services read `false, resolved` where the answer is not known
(conditional-beans Task 7b, ruled 2026-10-22). Which keys the container reads, how it splits
them, and what it falls back to are the framework's, so they are read off the jars before the
config model (`src/sextant/catalogs/spring-web.yml`, `config_model.profiles`) names them.

anything, and **not the version of the directory this harness found the jars under** — the

## What the rows say

**Rows 1 and 2 — three keys and one name.** `spring.profiles.active` lists the active
profiles, `spring.profiles.include` lists profiles active beside them, and
`spring.profiles.default` lists the profiles active when no other is; the reserved default
profile is `default`. These are `config_model.profiles`'s `active_keys`,
`include_keys`, `default_keys` and `default_profile`.

**Rows 3 and 4 — a value is a comma-separated list, or a list.** Boot reads each kind with
`Environment.getProperty`, removes every whitespace character and splits on commas, and
binds the same key as a `Set<String>` — so `h2, spring-data-jpa` and a YAML list
(`spring.profiles.active[0]`, `[1]`, as the config reader flattens it) both name two
profiles.

**Rows 5 and 6 — the default profiles are accepted only where no profile is active, and an
included profile is active.** `getAccepted` returns the active list unless it is empty, and
the active list is the `ACTIVE` kind plus the additional profiles the constructor is handed
— which `ConfigDataEnvironment.withProfiles` fills with `getIncludedProfiles`. So a set
`spring.profiles.include` is active everywhere it is read, and it, like a set
`spring.profiles.active`, keeps `default` from being accepted.

**Row 7 — only the base configuration sets them.** A profile-specific resource that sets
`spring.profiles.active`, `spring.profiles.include` or `spring.profiles.default` (or their
`[0]`) is refused by `InvalidConfigDataPropertyException`. So the keys are read from the base
environment's resolved configuration, and a profile file contributes only its own name.

## What this does NOT measure

* **Which activation selects a profile file's environment, and whether it replaces or extends
  the base's `spring.profiles.active`.** A profile FILE's environment is reached by an
  activation outside the module — a command-line `--spring.profiles.active`, the
  `SPRING_PROFILES_ACTIVE` environment variable, a test annotation — and a higher-precedence
  property source REPLACES the base's value of the key rather than adding to it, which is
  Boot's documented property-source precedence and not something this bytecode proves. Whether
  the deployment's activation for `p` also names a profile the base lists is the
  deployment's, not the code's; so in a profile-file environment, a profile named only in the
  base's `spring.profiles.active` is `unresolved`, while `p` itself and the base's
  `spring.profiles.include` (row 6: added whatever the active list is) are active. A
  documented claim, not a measurement.
* **Profile groups.** Row 5's `spring.profiles.group` / `expandProfiles` expand an active
  profile into a group's members; this analysis does not read groups, so a profile active only
  through a group reads as not active.
* **A placeholder nobody fills.** `${apollo_profile}` resolves at run time to whatever the
  deployment supplies; where the config layer leaves the key unresolved, every profile the
  rules above do not decide is `unresolved` there.
