# A2 Task 8 — the JDK `HttpRequest.Builder` and Apache HttpClient 5 request surfaces

**Question.** `jdk-httpclient.yml` and `apache-httpclient.yml` (spec §12) are
`okhttp.yml`'s shape: a static root, verb-setting steps, a `build` terminal joined to
the client's executing call through the argument `source` id. The JDK root seeds
`http_method: GET` — the platform's own documented default for a fresh builder — and,
exactly as for OkHttp (`w53_okhttp_verb_setters.md`), that seed is safe only while
EVERY verb-setting method on the builder is a declared step: an undeclared one passes
through uncaptured and leaves the seed standing as a confidently wrong verb. So each
builder is enumerated whole rather than filtered to the names the catalog already
knows, and the catalog's claim is compared against what the archive declares.

Run: `scripts/probes/a2t8_http_client_builders/run.sh`. Everything under
`## Observations` is that script's own output, pasted verbatim.

**Version scope (§5.4).** Read against **JDK 21.0.12.1** (`java.net.http` and
`java.base`; Temurin 21.0.12.1+1), **httpcore5 5.2.4** and **httpclient5 5.2.3**. The
JDK version is the one `$JAVA_HOME/release` states and `javap -version` prints; the two
jars state theirs in `META-INF/MANIFEST.MF`. `httpclient5` 5.2.3 pins `httpcore5` 5.2.4
through its parent POM's `httpcore.version`, which is why the core jar is measured at
5.2.4 and not at a version sharing the client's number. A JDK release between 21 and
today's is unverified: `HEAD()` is a `default` method the builder gained at 21, so an
older platform declares one verb setter fewer and the same catalog is complete there
too, but nothing here measured it.

## Expectation table

| # | If | then |
|---|---|---|
| 1 | every builder method that sets a verb is encoded | the JDK root's seeded GET is safe, and `test_defaulted_identity_values.py` may allowlist it on that condition |
| 2 | the builder declares a verb setter the catalog misses | the seed is unsafe and the allowlist entry is false |
| 3 | `java.net.URI` declares a constructor whose argument 0 is not the address | a `url_via` form on `<init>` — which matches by owner and method, with no arity — would read that argument as the address; the form is not declared, and the boundary is stated |
| 4 | `execute` has overloads taking the request at a position other than 0 | the execute-join reads every argument's `source`, so position does not matter to it; recorded so the terminal's claim is bounded |

## What the run found, in one paragraph

Every verb setter the JDK builder declares is encoded (five verb methods plus the
generic `method(String, BodyPublisher)`); nothing encoded is absent from the JDK. The
one root NOT encoded, `newBuilder(HttpRequest, BiPredicate)`, copies another request
and carries that request's verb — the seeded GET is wrong for it, which the catalog
states. `java.net.URI` declares FIVE constructors, four of them multi-argument with the
scheme at argument 0 — expectation 3's case, so only `URI.create(String)` is followed.
Apache's `ClassicRequestBuilder` declares three overloads of each of eight verb
factories plus the generic `create(String)`, all encoded; every `HttpGet`-family class
declares exactly two constructors (`String`, `URI`), the constructor form the catalog
does not yet read (`apache-httpclient-constructors`); `CloseableHttpClient.execute` has
eight overloads, the request at argument 0 or 1, all joined by `source`.
