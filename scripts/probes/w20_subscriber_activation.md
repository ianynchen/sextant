# OI-64 — construction is not subscription (GUIDELINES §8.6)

Run: `scripts/probes/w20_subscriber_activation/run.sh`. Everything below the rule is
that script's own output, pasted verbatim.

**Version scope (§5.4).** Read against **google-cloud-pubsub 1.127.3**, **api-common
2.31.0** and **spring-cloud-gcp-pubsub 5.1.2**, each self-reported by the archive; the
run aborts when a jar's self-report disagrees with the coordinate that resolved it.

## What was wrong

`google-pubsub-subscriber.yml` derived a live inbound `pubsub` endpoint from
`Subscriber.newBuilder(subscription, receiver).build()` — construction alone. Its own
comment defended this: *"the registration is the evidence, so this style needs no
execute-terminal."*

**Our own acceptance fixture was an instance of the defect.**
`RawPubSubSubscribers.java` built two subscribers and started neither, and both were
published as endpoints that `tests/application/test_interface_engine.py` asserted were
correct. The suite protected the fabrication, which is why nothing noticed it.

This is an over-report, and this project ranks those above under-reports — ARCHITECTURE's
*"the failure mode is fabrication, not imprecision"*. A missing row is silence; these
rows were a claim that a wire existed. And `protocol` is the column DR-5 links on, so a
fabricated inbound `pubsub` endpoint can merge into another consumer's graph.

## What the run establishes

**Construction is not subscription.** `Subscriber` extends `AbstractApiService` and
implements `ApiService` — an ordinary start/stop service object — and declares
`startAsync` itself. Nothing is delivered until it runs.

**There is no `@Bean` exception, and GUIDELINES §8.6 claimed one.** §8.6's worked example
read: *"a `@Bean` method returning a `Subscriber` — no call in this module starts it, and
it is still traced: the bean declaration is a fact, Spring starts a `Subscriber` bean is
a measured rule."* Nobody had measured it. Section 1 walks the whole hierarchy and finds
**no Spring lifecycle interface anywhere** — not `Lifecycle`, `SmartLifecycle`,
`InitializingBean` or `SmartInitializingSingleton` — and section 3 finds spring-cloud-gcp
ships no `BeanPostProcessor` that would start one. Spring does not start arbitrary beans.
So a `@Bean` returning a `Subscriber` is the same unstarted object as any other.

That is §8.6 violating its own rule, in the paragraph that says *the framework-rule link
is exactly the link that must be measured (§8.1), because assuming it fabricates the
whole trace rather than one step of it.* The rule stands; the example was an assumption
dressed as a measurement, and is now corrected in place.

## What ships

`registration.started_by` — an ordered chain of calls that must FOLLOW a registration
before it is a boundary, each linked receiver-to-result. This catalog declares
`Subscriber$Builder.build` then `Subscriber.startAsync`.

Chain reconstruction is within-method only (D00 §5), so three outcomes rather than two,
and the middle one is the reason this is not simply a stricter rule:

| the built subscriber is… | answer | why |
|---|---|---|
| started in the same method | a row | the whole chain is present |
| returned to a caller | a `registration_activation` question | a factory is ordinary code and its caller may start it; we cannot join the two here, and answering "no boundary" would trade a fabricated row for a silent false negative |
| built and dropped | silence | nothing can start it — it never leaves the method. Provably not a boundary |
